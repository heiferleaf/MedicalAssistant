# 分布式架构优化 — 需求用例文档（修订版）

> **项目阶段**: 课程设计/毕设（展示分布式架构能力）
> **核心约束**: 保持前端访问接口不变，前端已完成不修改
> **架构约束**: 模块化单体保持不变，共享数据库，不做服务发现/分布式事务/数据库拆分
> **优化方向**: 事件发布正确性、延迟任务可靠性、MQ 异步操作
> **时间预算**: 2 周
> **团队**: 5 名后端开发，并行开发

---

## 一、优化目标

在保持模块化单体架构的前提下，通过分布式消息模式提升系统可靠性与异步能力：

| 方向 | 目标 | 答辩展示点 |
|------|------|-----------|
| 事件驱动架构 | ApplicationEvent → DomainEvent + RabbitMQ | 异步解耦、最终一致性 |
| 分布式协调 | 分布式锁（Redisson） | 并发安全保障 |
| 服务治理 | 限流降级（Sentinel）、链路追踪 | 可观测性、高可用 |
| 消息可靠性 | RabbitMQ confirm/ACK/DLQ | 消息不丢失、不重复 |

## 二、用例清单

### U1: DomainEvent 驱动改造

**触发条件**: 业务状态变更
**参与者**: 2 人

#### 用例描述
将当前基于 `ApplicationEventPublisher` 的进程内事件，改造为基于 RabbitMQ 的 `DomainEvent`，实现异步通信和跨模块解耦。

#### 子用例

| ID | 子用例 | 描述 | 优先级 |
|----|--------|------|--------|
| U1.1 | 事件发布改造 | 业务代码中的 `publishEvent()` 改为 `DomainEventPublisher.publish()` | P0 |
| U1.2 | 事件消费者实现 | 为每个关键事件实现 DomainEventHook | P0 |
| U1.3 | 事件溯源日志 | 所有 DomainEvent 写入 DB 事件表，支持审计回溯 | P1 |
| U1.4 | 死信队列处理 | DLQ 消息的监控和手动重试机制 | P1 |

#### 需要改造的事件

| 当前事件 | 发布者 | 改造为 | 消费者 |
|---------|--------|--------|--------|
| FamilyMedicineAlarmEvent | TaskServiceImpl, DynamicTaskScheduler | DomainEvent(medication.alarm) | notification-hook (推送), sms-hook (短信) |
| FamilyMedicineUpdateEvent | TaskServiceImpl | DomainEvent(medication.updated) | family-hook (更新缓存), notification-hook |
| FamilyMemberUpdateEvent | FamilyGroupServiceImpl | DomainEvent(family.member.changed) | medical-hook (清理关联), notification-hook |
| FamilyHealthDataUpdateEvent | HealthDataServiceImpl | DomainEvent(health.data.updated) | family-hook (更新快照), notification-hook |
| UserTaskMedicineRemindEvent | DynamicTaskScheduler | DomainEvent(medication.remind) | notification-hook |

#### 验收标准
- [ ] 业务代码不再使用 `ApplicationEventPublisher` 发布跨服务事件
- [ ] 每个事件在 RabbitMQ 中有对应的消费者和处理逻辑
- [ ] 事件处理失败自动进入死信队列
- [ ] 事件表可查询历史事件记录

### U2: 分布式锁与并发控制

**触发条件**: 多实例并发访问共享资源
**参与者**: 1 人

#### 用例描述
将现有的 Redisson 本地锁升级为分布式感知的锁机制，并在关键业务场景引入分布式锁保护。

#### 子用例

| ID | 子用例 | 描述 | 优先级 |
|----|--------|------|--------|
| U2.1 | 分布式锁工具封装 | 基于 Redisson 封装通用分布式锁注解 `@DistributedLock` | P0 |
| U2.2 | 用药任务状态更新加锁 | 防止同一任务被多实例重复处理 | P0 |
| U2.3 | 家庭成员操作加锁 | 防止同一家庭并发邀请/踢出冲突 | P0 |
| U2.4 | AI 工具执行加锁 | 防止同一用户并发触发敏感操作 | P1 |

#### 验收标准
- [ ] `@DistributedLock(key="#taskId")` 注解可直接加在方法上
- [ ] 锁超时自动释放，不会死锁
- [ ] 并发测试：同一任务同时被两个请求处理时，只有一个成功

#### 用例描述

#### 子用例

| ID | 子用例 | 描述 | 优先级 |
|----|--------|------|--------|
| U3.1 | Sentinel Dashboard | Docker 部署 Sentinel 控制台 | P0 |
| U3.2 | 接口限流 | 对 `/api/agent/chat` 等 AI 接口设置 QPS 限流 | P0 |
| U3.3 | 热点参数限流 | 对用户维度限流，防止单用户刷接口 | P1 |

#### 限流规则示例

| 接口 | 限流类型 | 阈值 | 降级策略 |
|------|---------|------|---------|

#### 验收标准

### U5: 消息可靠性保障

**触发条件**: 消息发送/消费
**参与者**: 与 U1 同人

#### 用例描述
增强 RabbitMQ 消息的可靠性，确保消息不丢失、不重复。

#### 子用例

| ID | 子用例 | 描述 | 优先级 |
|----|--------|------|--------|
| U5.1 | 消息持久化确认 | 发布消息时开启 confirm 模式，确认 Broker 收到 | P0 |
| U5.2 | 消费端手动 ACK | 消费成功后才确认，失败重新入队 | P0 |
| U5.3 | 死信队列监控 | DLQ 消息数量告警 + 控制台查看 | P1 |
| U5.4 | 消息对账 | 定时检查已发送 vs 已消费的消息数量 | P2 |

#### 验收标准
- [ ] RabbitMQ 重启后，未消费的消息不丢失
- [ ] 消费失败的消息自动重试 3 次后进入死信队列
- [ ] 死信队列中的消息可通过管理界面手动重发

## 四、接口不变保证

前端访问接口路径和参数格式保持不变，Nginx 静态路由保持不变。前端无感知后端架构优化。

| 接口 | 路由方式 | 说明 |
|------|---------|------|
| `/api/user/*` | nginx → user-service | 保持不变 |
| `/api/plan/*`, `/api/task/*`, `/api/medicine/*` | nginx → medication-service | 保持不变 |
| `/api/family/*` | nginx → family-service | 保持不变 |
| `/api/health/*` | nginx → health-service | 保持不变 |
| `/api/agent/*` | nginx → agent-service | 保持不变 |
| `/ws` | nginx → notification-service | 保持不变 |

## 五、排除项说明

以下方案在评估后决定不采用：

| 方案 | 原因 |
|------|------|
| Nacos 服务注册发现 | 模块化单体架构下，Nginx 静态路由已满足需求，引入 Nacos 增加运维复杂度 |
| Seata 分布式事务 | 共享数据库下本地事务已足够，无需分布式事务 |
| 数据库拆分 | 当前数据量和并发量无需分库，拆分增加跨库查询复杂度 |
| OpenFeign 跨服务调用 | 保持直接 Java 方法调用，性能更优，调试更方便 |
