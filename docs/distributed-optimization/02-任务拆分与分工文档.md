# 分布式架构优化 — 任务拆分与分工文档（修订版）

> **时间**: 2 周（10 个工作日）
> **团队**: 5 名后端开发（Dev1 ~ Dev5）
> **核心约束**: 接口不变，前端不改，保持模块化单体架构
> **优化方向**: 事件驱动、分布式锁、限流降级、链路追踪、消息可靠性

## 二、各开发者任务详情

### Dev1: 事件驱动架构师（DomainEvent + 消息可靠性）

**角色**: 核心改造，影响全局

| 任务 | 需求用例 | 工作日 | 产出 |
|------|---------|--------|------|
| DomainEvent 发布改造 | U1.1 | 2天 | 修改 `TaskServiceImpl`, `DynamicTaskScheduler`, `FamilyGroupServiceImpl`, `HealthDataServiceImpl` |
| 事件溯源表 + 查询接口 | U1.3 | 1天 | `domain_event` 表 + 查询 API |
| RabbitMQ confirm 模式 | U5.1 | 0.5天 | `RabbitMqConfig` 增加 confirm callback |
| 消费端手动 ACK | U5.2 | 0.5天 | 各 Listener 改为 manual ACK |

**产出目录**:
```
common/infra/event/
  └── DomainEventPublisher.java          # 事件发布器改造
common/infra/event/
  └── EventAuditLog.java                 # 事件溯源实体
db/event_audit.sql                       # 事件审计表 DDL
common/config/
  └── RabbitMqConfig.java                # confirm 模式配置
```

**技术要点**:
- `ApplicationEventPublisher.publishEvent()` → `DomainEventPublisher.publish(new DomainEvent(...))`
- 事件发布时记录到 `domain_event` 表
- RabbitMQ 开启 publisher confirm，确认 Broker 收到

### Dev2: 事件消费架构师（DomainEventHook + 延迟任务）

**角色**: 事件消费端实现

| 任务 | 需求用例 | 工作日 | 产出 |
|------|---------|--------|------|
| DomainEventHook 实现 | U1.2 | 2天 | 5 个 Hook 类 |
| 死信队列监控 | U1.4 / U5.3 | 1天 | DLQ 消息查看接口 |
| 延迟任务可靠性 | U6.1 / U6.2 | 1天 | 重启恢复 + 失败重试 |

**产出目录**:
```
common/infra/event/hooks/
  ├── MedicationAlarmHook.java           # 用药告警 → 推送
  ├── MedicationUpdatedHook.java         # 药品变更 → 缓存更新
  ├── FamilyMemberChangedHook.java       # 家庭成员变更 → 关联清理
  ├── HealthDataUpdatedHook.java         # 健康数据更新 → 快照刷新
  └── MedicationRemindHook.java          # 用药提醒 → 推送
common/infra/delay/
  └── DelayTaskRecovery.java             # 延迟任务重启恢复
```

**技术要点**:
- 每个 Hook 实现 `DomainEventHook` 接口（hookName/supports/handle/order）
- 使用 `@ConditionalOnProperty` 控制激活
- 幂等性由 `DomainEventHookExecutor` 自动处理（Redis SETNX）
- 延迟任务存储在 Redis ZSET，支持重启后扫描恢复

### Dev3: 服务治理架构师（分布式锁 + Sentinel）

**角色**: 独立工作，不依赖其他人

| 任务 | 需求用例 | 工作日 | 产出 |
|------|---------|--------|------|
| @DistributedLock 注解封装 | U2.1 | 1天 | AOP 切面 + Redisson 锁 |
| 用药任务并发控制 | U2.2 | 0.5天 | TaskServiceImpl 加锁 |
| 家庭成员操作加锁 | U2.3 | 0.5天 | FamilyGroupServiceImpl 加锁 |
| Sentinel Dashboard 部署 | U3.1 | 0.5天 | Docker Compose 配置 |
| 接口限流规则 | U3.2 | 0.5天 | Sentinel 限流配置 |

**产出目录**:
```
common/lock/
  ├── DistributedLock.java               # 注解
  ├── DistributedLockAspect.java         # AOP 切面
  └── LockKeyResolver.java              # SpEL 键解析
docker/sentinel/                         # Sentinel Dashboard Docker
common/config/
  └── SentinelConfig.java               # Sentinel 初始化
```

**技术要点**:
- `@DistributedLock` 基于 Redisson `RLock`，AOP 切面拦截注解方法
- SpEL 解析锁键：`@DistributedLock(key="#taskId")`
- Sentinel 限流通过 `@SentinelResource(value="xxx", blockHandler="yyy")` 声明

## 五、排除项说明

以下方案在评估后决定不采用：

| 方案 | 原因 |
|------|------|
| Nacos 服务注册发现 | 模块化单体下 Nginx 静态路由已够用，引入 Nacos 增加运维复杂度 |
| Seata 分布式事务 | 共享数据库下本地事务已足够，无需分布式事务 |
| 数据库拆分 | 当前数据量和并发量无需分库，拆分增加跨库查询复杂度 |
| OpenFeign 跨服务调用 | 保持直接 Java 方法调用，性能更优，调试更方便 |
