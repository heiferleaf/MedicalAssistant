# MedicalAssistant 分布式迁移概要设计文档

## 1. 文档说明

本文档描述 MedicalAssistant 分布式迁移的总体架构、核心模块设计、关键数据流、部署结构、可靠性策略和迁移步骤。设计目标是在不一次性完全拆库拆服务的前提下，把现有系统从偏单 JVM 的实现迁移为可多实例部署、可观测、可扩展的分布式架构。

## 2. 设计原则

- 先模块化，后物理拆分：优先建立清晰边界和基础设施契约，不急于拆独立数据库。
- 核心业务短路径：登录、任务、药品、家庭、健康接口不被 AI、PDF、推送、延迟任务拖慢。
- 状态外置：WebSocket 路由、延迟任务、会话上下文、幂等状态迁移到 Redis / MySQL / RabbitMQ。
- 事件驱动：业务 Service 只发布领域事件，不直接执行推送、短信、缓存刷新等副作用。
- 显式配置：所有基础设施能力通过 profile 显式启用，禁止隐式默认启动。
- 可观测和可回滚：每个迁移阶段都能监控、压测、回滚。

## 3. 总体架构

### 3.1 目标服务结构

```text
Client / App / Web
        |
        v
Nginx / Gateway
        |
        +--> user-service          用户、登录、JWT
        +--> medication-service    药品、计划、服药任务
        +--> family-service        家庭组、成员、邀请、家庭事件
        +--> health-service        健康数据、健康快照
        +--> agent-service         Agent、RAG、OCR、Predict
        +--> notification-service  WebSocket、短信、站内通知
        +--> scheduler-service     延迟任务、补偿任务

Shared Infrastructure:
  MySQL / Redis / RabbitMQ / Object Storage / Metrics / Logs
```

### 3.2 当前过渡形态

短期内各服务可以继续来自同一代码仓库和同一镜像，通过不同 `MAIN_CLASS` 和 profile 启动。数据库可以暂时共库，跨模块协作通过事件和共享基础设施过渡。

关键要求：

- 每个 profile 明确扫描包和基础设施能力。
- 跨容器协作不依赖 Spring 本地 `ApplicationEvent`。
- WebSocket 连接只由 notification-service 维护。
- 延迟任务只由 scheduler-service 消费。

## 4. 服务职责设计

| 服务 | 职责 | 不应承担 |
| --- | --- | --- |
| user-service | 用户注册登录、JWT、个人信息、账号安全 | 家庭成员查询、WebSocket 推送、延迟任务消费 |
| medication-service | 药箱、用药计划、每日任务、打卡、任务状态事件 | 本机定时器、直接 WebSocket 推送 |
| family-service | 家庭组、成员、申请邀请、家庭事件日志、权限 | 维护 WebSocket session |
| health-service | 健康数据录入、健康趋势、健康异常事件、家庭快照失效 | 直接通知在线用户 |
| agent-service | Agent 会话、RAG、OCR、Predict、工具调用 | 核心业务同步阻塞、通知连接管理 |
| notification-service | WebSocket 连接、用户在线路由、推送消费、短信 Hook | 业务数据主写入、延迟任务调度 |
| scheduler-service | 延迟任务抢占、提醒、漏服检测、邀请过期、补偿任务 | 用户 WebSocket 会话维护 |
| gateway/nginx | 路由、TLS、静态资源、限流入口 | 业务状态存储 |

## 5. 基础设施设计

### 5.1 Profile 与能力开关

所有基础设施能力必须显式配置：

```yaml
service:
  websocket:
    enabled: false

infra:
  legacy-scheduler:
    enabled: false
  delay:
    redis:
      enabled: false
  domain-consumer:
    enabled: false
```

推荐启用关系：

| profile | websocket | delay redis consumer | legacy scheduler | domain consumer |
| --- | --- | --- | --- | --- |
| user | false | false | false | false / 可选 |
| medication | false | false | false | true |
| family | false | false | false | true |
| health | false | false | false | true |
| agent | false | false | false | 可选 |
| notification | true | false | false | 可选 |
| scheduler | false | true | false | 可选 |

### 5.2 线程池

统一在 `common/infra/async` 配置命名线程池：

| 线程池 | 用途 | 拒绝策略 |
| --- | --- | --- |
| `domainEventExecutor` | 领域事件 Hook、轻量异步副作用 | 可使用 CallerRuns 或受控降级 |
| `wsPushExecutor` | WebSocket 推送、Redis Pub/Sub 转发 | 队列可控，失败记录 |
| `aiExecutor` | AI / RAG / OCR / Predict 慢任务 | `AbortPolicy`，返回系统繁忙 |
| `pdfExecutor` | PDF 生成和导出 | 独立队列，避免占用 AI 线程 |

要求：

- 线程池暴露 active、pool size、queue size、rejected count。
- MDC / traceId 在线程切换时传播。
- AI 线程池队列容量独立配置，避免慢任务堆积。

### 5.3 连接池

建议配置起点：

- Tomcat max threads：200。
- Hikari maximum pool size：30。
- Redis lettuce max-active：64。
- 外部 HTTP client max connections：200，per route：50。

最终数值以压测结果调整。

## 6. 领域事件与消息设计

### 6.1 领域事件模型

```text
DomainEvent
  eventId
  eventType
  aggregateType
  aggregateId
  userId
  groupId
  occurredAt
  traceId
  payload
```

事件类型示例：

- `medication.task.status.changed`
- `medication.plan.changed`
- `family.member.changed`
- `family.alarm.created`
- `health.data.changed`
- `agent.task.completed`
- `ws.push.user`
- `cache.invalidate.family.snapshot`

### 6.2 RabbitMQ 拓扑

```text
exchange: medical.domain.topic
  medication.*        -> queue.medication.event
  family.*            -> queue.family.event
  health.*            -> queue.health.event
  ws.push.*           -> queue.ws.push
  ai.task.*           -> queue.ai.task
  cache.invalidate.*  -> queue.cache.invalidate

exchange: medical.delay.topic
  medication.remind        -> queue.delay.medication.remind
  medication.missed        -> queue.delay.medication.missed
  family.invite.expire     -> queue.delay.family.invite

exchange: medical.dlx.topic
  failed.# -> queue.dead.letter
```

设计要求：

- 所有业务队列 durable。
- 所有业务队列配置 DLX。
- RabbitTemplate 开启 publisher confirm / returns，避免 routing key 不匹配静默丢失。
- 建议增加 audit 队列或 fallback binding 捕获未匹配事件。

### 6.3 Hook 执行链

Hook 执行策略：

1. 业务 Service 完成主事务。
2. 事务提交后发布 DomainEvent。
3. Hook Executor 按事件类型选择 Hook。
4. 每个 Hook 独立幂等和独立 try-catch。
5. 单个 Hook 失败记录日志并进入重试，不中断其他 Hook。

典型 Hook：

- `MedicationTaskStatusChangedHook`
- `MedicationPlanChangedHook`
- `FamilyMemberChangedHook`
- `HealthDataChangedHook`
- `AgentTaskCompletedHook`
- `WsPushHook`
- `SmsNotifyHook`
- `CacheInvalidateHook`

## 7. WebSocket 与通知设计

### 7.1 推送链路

```text
业务服务
  发布 FamilyPushEvent / UserTaskMedicineRemindEvent / DomainEvent
        |
        v
ApplicationEventWsPushBridge / DomainEventHook
        |
        v
RabbitMQ: medical.domain.topic, routing key ws.push.user
        |
        v
queue.ws.push
        |
        v
notification-service: WsPushMessageListener
        |
        v
WsPubSubBroadcaster / WebSocketSessionManager
        |
        v
用户 WebSocket 连接
```

### 7.2 在线路由

Redis key 设计：

```text
ws:route:user:{userId} -> instanceId
ws:online:user:{userId} -> heartbeat state
ws:node:{instanceId} -> Redis Pub/Sub channel
```

要求：

- 路由和在线状态必须有 TTL。
- WebSocket 心跳刷新 TTL。
- 用户断开连接时清理本地 session 和 Redis 路由。
- 同一用户支持多个 session，不能用单 session 覆盖。

### 7.3 本地发送安全

Spring WebSocket `sendMessage` 不是线程安全的。设计上必须满足：

- 每个 session 串行发送。
- 或注册时使用 `ConcurrentWebSocketSessionDecorator`。
- 发送失败后清理 session，避免持续错误。

### 7.4 通知扩展

短信、站内通知、邮件等通过通知 Hook 接入。短信 Hook 失败不能影响 WebSocket 推送。

家庭服药告警短信路径：

```text
FamilyPushEvent(MEDICINE_ALARM)
  -> SmsNotifyHook
  -> 查询家庭组 owner
  -> 获取手机号
  -> 调用短信网关或记录待发送日志
```

## 8. 延迟任务设计

### 8.1 任务模型

```text
DelayTask
  taskId
  taskType
  bizId
  executeAt
  createdAt
  retryCount
  maxRetry
  payload
```

任务类型：

- `medication.remind`
- `medication.missed`
- `family.invite.expire`
- `agent.task.timeout`

### 8.2 Redis ZSet 实现

Redis 结构：

```text
key: delay:tasks
score: executeAt timestamp
value: DelayTask JSON
```

消费流程：

1. scheduler-service 定时轮询到期任务。
2. 使用 Lua 原子执行 `ZRANGEBYSCORE + ZREM` 抢占任务。
3. 根据 `taskType` 分发给对应 `DelayTaskHandler`。
4. 执行成功记录指标。
5. 执行失败更新 retryCount，按退避时间重新入队。
6. 超过最大重试进入死信 / 补偿表。

### 8.3 可靠性要求

- 多 scheduler 实例并发时，同一任务只能被一个实例抢到。
- 实例重启不丢任务。
- 任务等待时长通过 `now - createdAt` 计算。
- 任务执行延迟通过 `now - executeAt` 计算。

## 9. 数据库与缓存设计

### 9.1 索引设计

建议补齐：

| 表 | 索引 | 用途 |
| --- | --- | --- |
| `medication_task` | `(status, task_date, time_point)` | 扫描到期未完成任务 |
| `medication_task` | `(user_id, task_date, status)` | 今日任务和统计 |
| `medication_task` | `(plan_id, task_date)` | 删除未来任务 |
| `medicine` | `(user_id, name)` 唯一 | 防止并发重复创建 |
| `health_data` | `(user_id, is_deleted, measure_time)` | 查询最近健康数据 |
| `family_member` | `(user_id, status, is_deleted)` | 查询用户家庭关系 |
| `family_event_log` | `(group_id, event_type, event_time)` | 查询家庭告警 |
| `agent_messages` | `(session_id, id)` | 会话消息分页和最后消息 |

### 9.2 SQL 优化

必须替换：

- 药品 ID 循环查询改为 `findByIds`。
- 家庭健康快照改为批量取成员、批量取健康数据、批量统计任务。
- Agent session 列表改为一次 SQL 返回最后消息。

### 9.3 缓存设计

热点缓存：

- 用户药品列表。
- 家庭成员列表。
- 家庭健康快照。
- 家庭告警列表。
- Agent / RAG / OCR / Predict 结果。

策略：

- TTL 增加随机抖动，避免雪崩。
- 不存在数据缓存空值，避免穿透。
- 热点 key 使用互斥锁或逻辑过期防击穿。
- 写操作通过领域事件主动失效。
- Canal 作为兜底一致性机制。

## 10. Agent / AI 设计

### 10.1 外部调用

所有外部 AI 调用统一接入 HTTP client：

```text
AgentOrchestratorService
RagService
OcrService
PredictService
        |
        v
UnifiedFlaskClient / AiHttpClient
        |
        v
Flask / LLM / OCR Provider
```

要求：

- connect timeout、read timeout、连接池统一配置。
- 调用耗时、错误率、超时率统一埋点。
- Predict 地址走 `${flask.base-url}`。

### 10.2 请求分级

同步接口：

- 简单问答。
- 轻量 RAG。
- 简单结构化查询。

异步接口：

- OCR 后复杂分析。
- Predict 风险分析。
- 多工具链 Agent 推理。
- 长时间报告生成。

异步流程：

```text
Client -> POST /api/agent/tasks
       <- taskId
agent-service -> queue.ai.task
aiExecutor 消费执行
结果写 MySQL / Redis
发布 agent.task.completed
notification-service 推送结果
Client 轮询或 WebSocket 接收
```

### 10.3 会话状态

设计要求：

- 使用数据库或 Redis-backed `ChatMemoryStore` 替代单机内存窗口。
- `memoryId` 与业务 `sessionId` 对齐。
- 工具调用显式传递 `sessionId` 和 `traceId`。
- 历史消息裁剪逻辑集中处理，避免数据库历史和模型上下文不一致。

### 10.4 降级

- `DASHSCOPE_API_KEY` 缺失时不创建 LLM Bean。
- Flask / LLM 超时返回明确降级文案。
- AI 线程池拒绝时返回“系统繁忙，请稍后重试”。
- AI 降级不得影响核心业务。

## 11. 部署设计

### 11.1 Docker Compose 微服务模式

部署组件：

- MySQL
- Redis
- RabbitMQ
- Nginx
- user-service
- medication-service
- family-service
- health-service
- agent-service
- notification-service
- scheduler-service

Nginx 路由：

- `/api/user/*` -> `user-service:8081`
- `/api/plan/*`、`/api/task/*`、`/api/medicine/*` -> `medication-service:8082`
- `/api/family/*` -> `family-service:8083`
- `/api/health/*` -> `health-service:8084`
- `/api/agent/*`、`/api/rag/*`、`/api/predict/*`、`/api/ocr/*` -> `agent-service:8085`
- `/ws` -> `notification-service:8086`

### 11.2 Nginx 动态解析

Docker 容器重建后 IP 会变化。Nginx 配置应使用 Docker DNS：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;
set $user_service http://user-service:8081;
proxy_pass $user_service;
```

验收：

- 后端容器重建后，通过 Nginx 访问不持续 502。
- `nginx -t` 通过后 reload。

## 12. 安全设计

- JWT 无状态鉴权，所有业务接口校验 token。
- 家庭组接口按角色和权限校验。
- 敏感数据脱敏展示和加密传输。
- API Key 仅通过环境变量注入服务端。
- 写操作使用幂等键或分布式锁防重复提交。
- 日志不得输出明文密码、token、API Key、身份证号等敏感字段。

## 13. 可观测设计

指标类别：

- HTTP：QPS、P50、P95、P99、5xx。
- JVM：内存、GC、线程。
- Tomcat：活跃线程、队列。
- Hikari：active、idle、pending、timeout。
- Redis：命中率、连接池等待、慢命令。
- RabbitMQ：队列积压、消费者数、ack/nack、死信。
- 线程池：active、queue size、rejected。
- 延迟任务：待执行数、执行延迟、重试、死信。
- WebSocket：在线用户、连接数、发送失败、路由缺失。
- AI：外部调用耗时、超时、熔断、降级。

日志要求：

- 所有跨线程、跨 MQ 链路携带 `traceId`。
- 消费失败记录 eventId、routingKey、consumer、retryCount。
- WebSocket 发送失败记录 userId、sessionId、instanceId。

## 14. 迁移实施计划

### 阶段 0：修正与基线

- 修正 Mapper 字段不一致。
- 修正旧 scheduler 明显 bug。
- 关闭 SQL stdout。
- 接入 Actuator / Micrometer。
- 建立压测脚本。

### 阶段 1：基础设施收口

- 显式 profile 开关。
- 线程池和连接池配置。
- 统一 HTTP client。
- RabbitMQ 拓扑和幂等服务。

### 阶段 2：事件与延迟任务

- 接入 DomainEvent。
- 接入 Hook Executor。
- 迁移服药提醒、漏服检测、邀请过期。
- 建立死信和补偿。

### 阶段 3：WebSocket 与通知

- notification-service 独占 WebSocket。
- `queue.ws.push` 推送链路。
- 在线路由 TTL。
- 多端连接。
- Nginx 动态解析。

### 阶段 4：数据与 AI

- 索引和批量 SQL。
- 缓存防击穿。
- AI 请求分级。
- Agent 会话共享。

### 阶段 5：多实例压测和上线

- 多实例联调。
- 核心业务压测。
- WebSocket 连接压测。
- 延迟任务唯一消费测试。
- Redis / RabbitMQ / Flask 故障演练。
- 出具上线和回滚方案。

## 15. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 服务边界不清，继续跨 Mapper 调用 | 后续拆服务困难 | 先定义接口和事件，逐步移除跨包实现依赖 |
| MQ routing key 不匹配导致消息丢失 | 推送、缓存失效、任务丢失 | 开启 confirm / returns，增加 fallback / audit 队列 |
| Hook 失败中断链路 | 非关键副作用影响主推送 | Hook 独立 try-catch，失败重试，不中断后续 Hook |
| WebSocket 并发发送不安全 | 推送异常、连接断开 | 每 session 串行发送或使用安全 decorator |
| Redis 延迟任务重复消费 | 重复提醒、重复状态写入 | Lua 原子抢占 + 消费幂等 |
| AI 慢调用拖垮核心业务 | 登录、任务、家庭接口变慢 | aiExecutor 隔离、限流、异步 taskId、降级 |
| 缓存雪崩或击穿 | MySQL 压力突增 | 随机 TTL、空值缓存、互斥重建 |
| Nginx 缓存旧容器 IP | 容器重建后 502 | Docker DNS 动态解析 |

## 16. 设计验收标准

- 服务职责矩阵与配置一致。
- 业务事件能跨容器投递。
- notification-service 能统一处理 WebSocket 推送。
- scheduler-service 能多实例唯一消费延迟任务。
- Agent 慢调用被隔离并可降级。
- 热点查询和缓存策略通过压测验证。
- 监控指标能定位 Web、DB、Redis、MQ、AI、WebSocket 的瓶颈。
- 所有关键迁移步骤具备回滚方案。
