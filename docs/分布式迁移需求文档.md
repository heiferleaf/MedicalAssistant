# MedicalAssistant 分布式迁移需求文档

## 1. 文档说明

本文档用于明确 MedicalAssistant 从单体 / 模块化单体向分布式部署迁移时的需求范围、业务目标、功能需求、非功能需求和验收标准。文档重点不重新定义全部业务功能，而是围绕“健康与药物管理系统在分布式场景下如何保持可用、一致、可扩展”展开。

## 2. 项目背景

MedicalAssistant 面向个人用户、被照护者、家庭成员和家庭管理员，提供用户与家庭组管理、药品识别、用药计划、服药提醒、健康数据监测、异常告警、AI 健康助手等能力。当前系统已经具备 Spring Boot、MyBatis、MySQL、Redis、RabbitMQ、WebSocket、Nginx、Docker Compose 等基础设施，也已经开始按 user、medication、family、health、agent、notification、scheduler 等入口拆分运行。

现有微服务模式仍存在以下迁移风险：

- 部分服务仍通过本 JVM 扫描其他模块 Mapper，服务边界不清晰。
- Spring `ApplicationEvent` 只能在本进程内传播，不能跨容器传递业务事件。
- WebSocket 连接保存在 notification-service 本机内存，其他业务容器不能直接推送。
- 服药提醒、漏服检测、邀请过期等任务若依赖本机调度，在多实例下会重复执行或丢失。
- AI / OCR / RAG / Predict 调用耗时长，若同步占用 Web 请求线程，会拖慢核心业务。
- 缓存、索引、连接池、线程池、监控、故障降级还需要面向高并发和多实例重新整理。

因此，本次迁移的目标是先形成“模块化单体 + 分布式基础设施”的稳定形态，再逐步演进为物理微服务。

## 3. 总体目标

### 3.1 业务目标

- 支持用户、家庭组、药品、用药计划、健康数据、AI 助手等核心业务在多容器环境下稳定运行。
- 保证服药提醒、漏服告警、健康异常、家庭消息等事件能跨实例可靠送达。
- 保证 AI 慢请求、OCR 识别、风险预测等重任务不会影响登录、任务打卡、家庭快照等核心接口。
- 支持家庭成员跨端协作，确保健康数据、用药状态、告警消息按权限共享和推送。
- 为后续拆分为独立 user-service、medication-service、family-service、health-service、agent-service、notification-service、scheduler-service 奠定边界基础。

### 3.2 技术目标

- HTTP 服务无状态化，任意实例可处理任意请求。
- 单 JVM 内存状态迁移到 Redis、MySQL 或 RabbitMQ。
- 业务副作用从 Service 直接调用改为领域事件、Hook、消息队列消费。
- 延迟任务从 `ScheduledFuture` 迁移到 Redis ZSet / MQ / MySQL 任务表等共享任务平台。
- WebSocket 推送从本地 session 直发升级为 notification-service 集中推送和跨实例路由。
- 建立连接池、线程池、熔断限流、指标监控和压测基线。

| 家庭组管理员 | 创建家庭组，邀请成员，管理权限，接收异常告警 | 远程了解被照护者健康与用药状态，及时干预 |

| 系统运维 / 开发人员 | 部署、监控、排障、扩容系统 | 能观测、能回滚、能定位瓶颈 |

| 模块 | 主要功能 | 分布式迁移关注点 |

| 药箱与用药计划 | 药品 CRUD、用药计划、每日任务、打卡、漏服 | 写操作幂等；任务生成和提醒延迟任务化 |

| 调度与补偿 | 服药提醒、漏服检测、邀请过期、补偿任务 | 多实例唯一消费；重试；死信；可观测 |

## 5. 功能性需求

### 5.1 服务边界与能力开关

#### FR-01 服务职责显式化

系统必须明确每个服务 profile 的职责：

- `user-service`：用户、登录、JWT、个人信息。
- `medication-service`：药品、计划、服药任务、漏服状态。
- `family-service`：家庭组、成员、邀请申请、家庭事件日志。
- `health-service`：健康数据、健康快照。
- `agent-service`：Agent 会话、RAG、OCR、Predict、工具调用。
- `notification-service`：WebSocket、短信、站内通知、推送消费。
- `scheduler-service`：延迟任务、补偿任务、批处理任务。
- `gateway/nginx`：路由、静态资源、TLS、限流入口。

验收标准：

- 每个 profile 的 `service.websocket.enabled`、`infra.delay.redis.enabled`、`infra.legacy-scheduler.enabled`、`infra.domain-consumer.enabled` 必须显式配置。
- 不允许因配置缺失导致默认启用关键基础设施能力。
- 启动日志应能看到当前实例启用的基础设施能力清单。

#### FR-02 模块依赖收敛

业务模块不得随意扫描其他领域 Mapper 来完成跨模块逻辑。短期允许 notification-service 或 scheduler-service 按职责读取必要数据，但必须通过明确的接口、事件或查询服务隔离。

验收标准：

- user-service 不依赖 family mapper。
- 业务 Service 不直接调用 WebSocket session 管理器。
- 业务 Service 不直接创建本机延迟定时器。

### 5.2 领域事件与 Hook

#### FR-03 统一领域事件模型

系统应建立统一 `DomainEvent` 模型，至少包含：

- `eventId`
- `eventType`
- `aggregateType`
- `aggregateId`
- `userId`
- `groupId`
- `occurredAt`
- `traceId`
- `payload`

首批接入事件：

- 用药任务状态变更。
- 用药计划变更。
- 家庭成员变更。
- 健康数据变更。
- AI 任务完成。
- 缓存失效。
- WebSocket 推送。

验收标准：

- 至少任务状态变更、家庭成员变更、健康数据变更三类事件走统一事件模型。
- 事件在事务提交后发布，避免事务回滚后仍推送错误状态。

#### FR-04 Hook 执行可靠性

业务动作后的副作用应通过 Hook 执行，包括缓存失效、家庭告警、短信通知、WebSocket 推送、AI 后处理等。

验收标准：

- 单个 Hook 失败不能中断后续 Hook。
- Hook 执行必须具备幂等键，建议使用 `eventId + hookName`。
- Hook 失败要记录日志并支持重试或进入死信 / 补偿清单。

### 5.3 消息队列与幂等消费

#### FR-05 RabbitMQ 拓扑

系统应使用 RabbitMQ 承载跨实例事件和削峰能力：

- `medical.domain.topic`：业务领域事件。
- `medical.delay.topic`：延迟任务事件或调度事件。
- `medical.dlx.topic`：死信事件。
- `queue.ws.push`：WebSocket 推送命令。
- `queue.ai.task`：AI 异步任务。
- `queue.cache.invalidate`：缓存失效。

验收标准：

- 所有 durable 队列绑定死信交换机。
- 不匹配 routing key 的消息不能静默丢失，应有 audit / fallback / confirm 机制。
- MQ 消费者必须具备幂等、重试、失败日志。

#### FR-06 消费幂等

所有消息消费和延迟任务消费必须防止重复副作用。

验收标准：

- 使用 Redis 或数据库记录 `RUNNING / DONE` 或等价幂等状态。
- 已完成消息在 TTL 内重复到达时直接跳过。
- 处理中失败应清理运行态或进入重试。

### 5.4 延迟任务平台

#### FR-07 延迟任务统一模型

系统应统一服药提醒、漏服检测、家庭邀请过期等延迟任务，任务体至少包含：

- `taskId`
- `taskType`
- `bizId`
- `executeAt`
- `createdAt`
- `retryCount`
- `maxRetry`
- `payload`

验收标准：

- 任务创建后进入 Redis ZSet / MQ / MySQL 任务表，不再只存本机内存。
- 多实例同时运行时，同一任务只执行一次。
- 任务执行延迟、等待时长、重试次数可观测。

#### FR-08 延迟任务重试与死信

延迟任务失败后应支持退避重试，超过最大重试次数后进入死信或补偿清单。

验收标准：

- 任务失败不会无限循环。
- 任务死信可查询、可人工补偿。
- scheduler-service 重启不丢任务。

### 5.5 WebSocket 与通知

#### FR-09 notification-service 统一推送

WebSocket 连接只能由 notification-service 维护，业务服务不得直接持有或发送 WebSocket session。

验收标准：

- 只有 `service.websocket.enabled=true` 的 notification-service 消费 `queue.ws.push`。
- `queue.ws.push` 消费者数量只随 notification listener 并发变化，不随业务服务数量变化。

#### FR-10 跨实例推送

系统应支持任意业务实例发布推送事件，用户连接在哪个 notification 实例都能收到。

验收标准：

- 用户连接到 notification A，业务事件由 medication / health / family / notification B 触发时，消息仍能送达。
- 同一用户多端连接时，所有连接都能收到。
- 对同一 session 发送必须串行化或使用安全包装，避免并发 `sendMessage` 异常。

#### FR-11 通知扩展

系统应为短信、站内通知等非 WebSocket 通知保留 Hook 扩展点。

验收标准：

- 家庭服药告警需保留 owner 手机号通知路径。
- 短信网关未接入时不能影响 WebSocket 主推送链路。

### 5.6 数据库与缓存

#### FR-12 热点 SQL 优化

系统应消除高频接口 N+1 查询，并补齐组合索引。

重点范围：

- 今日任务。
- 历史任务。
- 药品列表。
- 家庭健康快照。
- 家庭告警。
- Agent session 列表。

验收标准：

- 主要 SQL 有 explain 记录并命中预期索引。
- 家庭快照不再按成员循环查询健康数据和任务统计。
- Agent session 列表不再逐 session 查询最后消息。

#### FR-13 缓存抗击穿与一致性

系统应对热点缓存提供随机 TTL、空值缓存、互斥重建或逻辑过期策略。

验收标准：

- 家庭成员、家庭健康快照、家庭告警、药品列表等热点数据具备缓存策略说明。
- 写操作后能通过领域事件或 Canal 兜底触发缓存失效。
- 缓存命中率、回源次数、重建失败数可观测。

### 5.7 Agent / OCR / RAG / Predict

#### FR-14 外部 AI 调用统一治理

所有 Flask / OCR / RAG / Predict 调用应统一使用带连接池、超时和指标的 HTTP client。

验收标准：

- 不再出现零散 `new RestTemplate()`。
- Predict 地址不硬编码 `localhost`，统一走 `${flask.base-url}`。
- 外部调用耗时、超时、错误率可观测。

#### FR-15 AI 请求分级

Agent 请求应分为短请求和长请求：

- 短请求：简单问答、轻量 RAG、轻量查询，允许同步返回。
- 长请求：OCR 后分析、复杂预测、多工具链推理，异步入队并返回 `taskId`。

验收标准：

- AI 高峰不拖慢登录、任务、家庭、健康等核心业务。
- AI 线程池满载时返回明确“系统繁忙 / 排队中”，不能让 HTTP 请求线程执行长任务。

#### FR-16 Agent 会话跨实例连续

Agent 会话上下文、工具执行上下文、消息历史应迁移到共享状态。

验收标准：

- 同一 session 请求打到不同 agent 实例时上下文连续。
- 异步线程或 MQ 消费线程中不依赖易丢失的 `ThreadLocal`。
- LLM Key 缺失时 agent-service 不崩溃，接口返回明确配置提示。

## 6. 非功能性需求

### 6.1 性能需求

| 指标 | 目标 |
| --- | --- |
| 核心业务接口 P95 | < 200 ms |
| 核心业务接口 P99 | < 500 ms |
| HTTP 5xx | < 0.1% |
| WebSocket 跨实例推送 P95 | < 1 s |
| 延迟任务到期执行延迟 P95 | < 2 s，按业务容忍度可调整 |
| 简单 Agent 问答 P95 | < 2 s |
| 缓存命中 RAG P95 | < 500 ms |
| OCR + 结构化解析 P95 | < 5 s |

### 6.2 可用性需求

- MySQL、Redis、RabbitMQ、Nginx、业务容器重启后系统能自动恢复。
- 单个 notification 实例重启不影响其他实例的在线推送。
- RabbitMQ 短时不可用时，业务主流程应尽量可提交，并保留补偿策略。
- AI / Flask / LLM 不可用时，核心业务仍可使用。

### 6.3 一致性需求

- 核心交易数据以 MySQL 为准。
- 缓存允许短暂最终一致，但必须有失效事件和回源机制。
- 事件发布与数据库事务应保证最终一致，后续可引入 outbox 表。
- 用药任务状态更新、家庭审批、创建计划等写操作必须幂等。

### 6.4 安全与隐私需求

- 用户密码不得明文存储，应使用安全哈希。
- 手机号、身份证号、病史、健康指标等敏感信息应脱敏展示、加密传输。
- JWT 鉴权保持无状态，所有核心接口必须鉴权。
- 家庭组数据共享遵循最小授权原则。
- 外部 API Key 只能通过服务端环境变量配置，不得暴露到前端。

### 6.5 可观测性需求

系统必须能观测：

- HTTP 请求耗时、错误率。
- Tomcat 线程。
- Hikari 连接池。
- Redis 连接池、命中率、慢命令。
- RabbitMQ 队列积压、consumer 数、ack/nack、死信。
- 各线程池活跃数、队列长度、拒绝次数。
- 延迟任务待执行数、执行延迟、重试数、死信数。
- WebSocket 在线连接数、发送成功/失败、路由缺失数。
- 外部 AI 调用耗时、错误率、熔断状态。

## 7. 迁移阶段需求

### 阶段一：压测前修正与能力收口

- 修正已知正确性问题。
- 关闭生产 SQL stdout。
- 收口基础设施开关。
- 建立服务能力矩阵和启动日志。
- 接入基础监控。

### 阶段二：基础设施和事件底座

- 建立统一线程池、连接池、HTTP client。
- 建立 DomainEvent、RabbitMQ 拓扑、幂等服务。
- 建立 Hook 执行框架。

### 阶段三：延迟任务和 WebSocket 迁移

- 服药提醒、漏服检测、邀请过期迁移到共享延迟任务。
- WebSocket 推送迁移到 `queue.ws.push` 和 notification-service。
- 在线路由支持 TTL 和多端连接。

### 阶段四：数据、缓存和 AI 隔离

- 补索引、批量查询、缓存防击穿。
- Agent / OCR / RAG / Predict 接入统一 HTTP client。
- 长 AI 请求异步化，结果通过轮询或 WebSocket 返回。

### 阶段五：多实例压测与治理

- 多实例运行 user、medication、family、health、agent、notification、scheduler。
- 完成核心业务、AI、WebSocket、延迟任务压测。
- 完成 Redis、RabbitMQ、Flask、单实例重启故障演练。

## 8. 验收标准

系统完成阶段性分布式迁移时，必须满足：

- 核心业务服务能在多实例下稳定运行。
- `queue.ws.push` 只由 notification-service 消费。
- 业务事件跨 JVM 传播，不依赖本地 `ApplicationEvent` 完成跨服务协作。
- 延迟任务多实例唯一消费，失败可重试，耗尽可死信。
- Agent 慢调用不拖垮核心业务线程。
- 热点 SQL 和缓存策略具备压测数据支撑。
- 容器重建后 Nginx 能重新解析服务，不持续 502。
- 所有上线改动具备回滚方案。
