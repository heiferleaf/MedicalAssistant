# 代办

## 修复记录

- 已补回家庭服药告警的短信扩展点：`ApplicationEventWsPushBridge` 发布 WebSocket 推送前会执行 `FamilyPushEventHook`，`FamilyMedicineAlarmSmsHook` 保留旧逻辑中“家庭组 owner 手机号”的查询路径。当前没有真实短信网关配置，因此先记录待发送日志，后续接入短信 SDK 时只需要替换 hook 内部发送实现。
- 已限制 WebSocket 推送 MQ 消费者只在显式开启的服务启动：`WsPushMessageListener` 改为 `matchIfMissing = false`，`notification` profile 开启，其他微服务 profile 关闭。
- 已将 Redis 延迟任务抢占改为 Lua 原子执行 `ZRANGEBYSCORE + ZREM`，避免多实例轮询时 `range + remove` 分离带来的竞态窗口。
- 已移除 `WsPushCommand.jsonPayload`，统一使用 `Map<String, Object> payload`，由监听器集中序列化。
- 已让家庭推送优先读取 `FamilyCacheService` 缓存，缓存没有命中时再回退查 `FamilyMemberMapper`。
- 已删除 `WsPushMessageListener` 外层冗余 `isDone` 调用，只保留 `tryStart` 作为幂等入口。
- 已给 AI 线程池增加独立 `infra.async.ai.queue-capacity` 配置，并改用 `AbortPolicy` 快速拒绝长耗时任务堆积。
- 已移除 `UserServiceApplication` 对 family mapper 和 `FamilyCacheService` 的 bootstrap 依赖，user 服务只扫描自身 mapper。
- 可用性补强：`DASHSCOPE_API_KEY` 未配置时不再创建 DashScope/MedicalAgent Bean，Agent 服务保持启动，聊天入口返回“LLM 未配置”的明确提示。
- 可用性补强：微服务容器重建后 Nginx 不再缓存旧 upstream IP，改用 Docker 内置 DNS 动态解析，避免重建 user/family 等服务后出现 502。

## 二、具体问题与建议

### 必须修复

#### 1. WsAlarmBroadcastListener 删除后留有功能缺口

旧的 `WsAlarmBroadcastListener` 被删除，但其中的 `SmsHandle` 短信逻辑（通过家庭组 owner 手机号）没有迁移到新实现。`ApplicationEventWsPushBridge` 只做了 WebSocket 推送，短信通知路径完全丢失。

```java
// 旧代码中存在但新代码里没有对应
private void SmsHandle(Long groupId) {
    Optional<String> phone = Optional.ofNullable(groupMapper.selectById(groupId))...
}
```

建议：确认短信功能是否有其他入口，或在 `ApplicationEventWsPushBridge` 中补一个 hook 点。

#### 2. WsPushMessageListener 仍然是 matchIfMissing = true

```java
// WsPushMessageListener.java:18
@ConditionalOnProperty(prefix = "service.websocket", name = "enabled", havingValue = "true",
matchIfMissing = true)
```

所有服务默认都会启动这个监听器，意味着 `user-service`、`medication-service` 等也在消费 `QUEUE_WS_PUSH` 队列。这和架构设计不符：只有 `notification-service` 应该消费 WebSocket 推送队列。

建议：改为 `matchIfMissing = false`，在 `application-notification.yaml` 里显式开启。

#### 3. RedisDelayTaskConsumer 的 range + remove 不是原子操作

```java
// RedisDelayTaskConsumer.java:43-51
Set<String> readyTasks = redisTemplate.opsForZSet()
        .rangeByScore(...);
for (String raw : readyTasks) {
    Long removed = redisTemplate.opsForZSet().remove(..., raw);
    if (removed == null || removed == 0) continue;
    handleRawTask(raw);
}
```

`rangeByScore` 和 `remove` 之间有竞态窗口。多实例同时轮询时，两个实例可能同时拿到同一批 task，再用 `remove` 抢占，虽然靠 `removed == 0` 做了二次过滤，但仍存在隐患：

- 如果任务在 `rangeByScore` 之后、`remove` 之前被其他实例删除并重新入队（retry），当前实例拿到的是旧副本，重新入队的新版本也在 ZSet 里，导致逻辑混乱。

建议：用 Lua 脚本原子化 `zrangebyscore + zrem`：

```lua
local items = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
for _, item in ipairs(items) do
    redis.call('ZREM', KEYS[1], item)
end
return items
```

或直接用 `zpopmin` 命令（Spring Data Redis 已支持）。

### 应当改进

#### 4. WsPushCommand 同时有 jsonPayload 和 payload 两个字段，职责不清

```java
// WsPushCommand.java:13-14
private String jsonPayload;
private Map<String, Object> payload = new HashMap<>();
```

`WsPushMessageListener` 消费时：

```java
// WsPushMessageListener.java:52-55
String payload = command.getJsonPayload();
if (!StringUtils.hasText(payload)) {
    payload = objectMapper.writeValueAsString(command.getPayload());
}
```

这是个双轨模型，两个字段互为备份，语义模糊，反序列化后究竟哪个有效不明确。生产者 `ApplicationEventWsPushBridge` 只填 `payload`（Map），`jsonPayload` 永远为 null，但字段还在。

建议：移除 `jsonPayload` 字段，统一只用 `Map<String, Object> payload`，序列化由 listener 统一处理。

#### 5. ApplicationEventWsPushBridge 对家庭推送事件做了一次额外 DB 查询

```java
// ApplicationEventWsPushBridge.java:47
List<Long> userIds = memberMapper.findActiveUserIdsByGroupId(groupId);
```

业务事件发布时，大部分场景已经知道影响的 userId 范围（例如任务状态变更事件），但这里放弃了事件携带的信息，重新查了一次 DB。相比旧代码用 Redis 缓存的家庭成员列表（`familyCacheService.getGroupMemberIds`），这次反而增加了 DB 压力。

建议：优先使用 Redis 缓存（`FamilyCacheService`）获取 groupId 对应的成员 ID，DB 作为 fallback；或者让事件本身携带 `List<Long> targetUserIds`。

#### 6. idempotencyService.isDone 和 tryStart 之间有 TOCTOU

```java
// WsPushMessageListener.java:44-48
if (idempotencyService.isDone(idempotencyKey)) return;
if (!idempotencyService.tryStart(idempotencyKey, RUNNING_TTL)) return;
```

`isDone` 用了 `hasKey`，`tryStart` 里又再次调用了 `isDone`，导致两次 Redis 调用，且 `isDone -> tryStart` 之间没有原子保证。极端情况下两个消费者都通过了 `isDone` 检查，再争抢 `setIfAbsent`，这是可以接受的（`setIfAbsent` 是原子的），但冗余的 `isDone` 调用没有必要：

```java
// MessageIdempotencyService.java:24-29
public boolean tryStart(String key, Duration ttl) {
    if (isDone(key)) return false;
    return Boolean.TRUE.equals(...setIfAbsent...);
}
```

调用方的外层 `isDone` 检查是多余的，反而增加 Redis RTT。建议直接调 `tryStart`，让 `tryStart` 内部统一处理。

#### 7. AsyncConfig 所有线程池共用同一个 queueCapacity

```java
// AsyncConfig.java:64
return buildExecutor("pdf-", pdfCoreSize, pdfMaxSize, queueCapacity / 2);
```

`pdfExecutor` 用了 `queueCapacity / 2`（250），但 `aiExecutor`、`wsPushExecutor`、`domainEventExecutor` 都用了 500。AI 任务通常是长耗时重量级任务，队列容量 500 意味着高峰时可能积压大量慢任务，反而不是好事。应该用更小的队列 + 快速拒绝，而不是允许大量排队。

建议：AI 线程池单独配置一个更小的 `queue-capacity`，例如 50-100，配合 `AbortPolicy` 快速返回“系统繁忙”，而不是 `CallerRunsPolicy`（后者会把调用方线程堵住）。

#### 8. UserServiceApplication 引入了 FamilyMemberMapper 但 family 边界并不属于 user 服务

```java
// UserServiceApplication.java:19
@MapperScan({"com.whu.medicalbackend.user.mapper", "com.whu.medicalbackend.family.mapper"})
@Import({RedisService.class, FamilyCacheService.class})
```

`user-service` 为了支持推送事件里的家庭成员查找，额外扫描了 family mapper。这把 user 和 family 两个边界耦合在了 bootstrap 层。长远看，应该让 family 逻辑留在 `family-service` 或 `notification-service`，`user-service` 不应该知道 family mapper 的存在。

## 三、做得好的地方

- MQ 拓扑设计清晰：domain exchange、delay exchange、DLX 三层分离，所有 durable 队列都绑了 dead letter exchange，失败后有地方可查。
- 幂等消费实现合理：`MessageIdempotencyService` 用 Redis 的 RUNNING / DONE 两态 key 控制幂等，逻辑清晰，TTL 配置合理。
- MDC 传播正确：`AsyncConfig` 用 `TaskDecorator` 在线程切换时传播 MDC，日志追踪能力保留完整。
- `@TransactionalEventListener` 使用正确：`ApplicationEventWsPushBridge` 用 `AFTER_COMMIT` 确保事务提交后再推送，避免事务回滚后推送了错误状态。
- `ObjectProvider` 处理 mapper 可选注入：`ApplicationEventWsPushBridge` 通过 `ObjectProvider<FamilyMemberMapper>` 做了优雅的条件依赖，不强依赖 family mapper 也不会崩溃。

## Code Review — 第二轮（基础设施层深查）

范围：`DomainEventHookExecutor`、`FamilyMedicineAlarmSmsHook`、`RabbitDomainEventPublisher`、`DelayTask`、`RabbitMqConfig`、`AsyncConfig`、`WsPubSubBroadcaster`、`DomainEvent`

---

### 必须修复

#### 1. DomainEventHookExecutor 单个 hook 失败会中断整个 hook 链

```java
// DomainEventHookExecutor.java:52
throw new IllegalStateException("Hook " + hook.hookName() + " failed", e);
```

任意一个 hook 抛出异常（例如短信 hook 因 mapper 为空报错），后续所有 hook（WebSocket 推送等）都不会执行。这是严重的可靠性问题：一个非关键的副作用 hook 导致核心推送也失败。

建议：每个 hook 单独 try-catch，记录错误后 continue，不中断后续 hook：

```java
for (DomainEventHook hook : hooks) {
    try {
        // 幂等检查 + 执行
        hook.handle(event);
    } catch (Exception e) {
        log.error("Hook {} failed for eventId={}, skipping", hook.hookName(), event.getEventId(), e);
    }
}
```

#### 2. WsPubSubBroadcaster.pushLocalSession 并发 sendMessage 不安全

```java
// WsPubSubBroadcaster.java:80-89（估算行号）
session.sendMessage(new TextMessage(payload));
```

Spring WebSocket 的 `WebSocketSession.sendMessage()` 不是线程安全的。`wsPushExecutor` 多线程并发向同一用户的多个 session 发送消息时，会抛出 `IllegalStateException: TEXT_PARTIAL_WRITING`。

建议：对每个 session 加同步锁，或改用 `ConcurrentWebSocketSessionDecorator` 包装 session：

```java
// 注册时包装
ConcurrentWebSocketSessionDecorator safe = new ConcurrentWebSocketSessionDecorator(session, 5000, 65536);
```

### 应当改进

#### 3. DomainEventHookExecutor 的 isDone + tryStart 仍是 TOCTOU

```java
// DomainEventHookExecutor.java:36-40（估算）
if (idempotencyService.isDone(idempotencyKey)) return;
if (!idempotencyService.tryStart(idempotencyKey, RUNNING_TTL)) return;
```

与已修复的 `WsPushMessageListener` 同样的问题：外层 `isDone` 调用是多余的，`tryStart` 内部已经包含相同检查，外层调用只增加了一次 Redis RTT 而不提供额外保证。

建议：直接调用 `tryStart`，移除外层 `isDone` 检查（与 `WsPushMessageListener` 修复方式相同）。

#### 4. FamilyMedicineAlarmSmsHook 每次都直接查 DB，无缓存

```java
// FamilyMedicineAlarmSmsHook.java:44-47
Optional<String> phone = Optional.ofNullable(groupMapper.selectById(event.getGroupId()))
        .map(FamilyGroup::getOwnerUserId)
        .map(userMapper::findByUserId)
        .map(User::getPhoneNumber);
```

服药告警是高频事件，每次告警都走两次 DB（`selectById` + `findByUserId`）。家庭组 owner 信息变化极低频，完全可以缓存。

建议：通过 `FamilyCacheService` 或 Spring Cache 获取家庭组 owner 信息，DB 作为 fallback。

#### 5. RabbitDomainEventPublisher 路由键静默丢消息风险

```java
// RabbitDomainEventPublisher.java:25（估算）
rabbitTemplate.convertAndSend(EXCHANGE_DOMAIN, event.getEventType(), event);
```

`event.getEventType()` 的值（如 `"medication.task.status.changed"`）直接作为 Topic exchange 的 routing key。如果任何绑定 pattern 不匹配，消息被静默丢弃，RabbitMQ 不会报错，也没有 fallback 路由。

建议：
1. 在 `RabbitMqConfig` 中为 domain exchange 加一个通配绑定（`#`）到 DLX 或 audit 队列，保证无匹配消息可追查。
2. 或在发送后用 `rabbitTemplate.setConfirmCallback` 确认 broker 收到。
3. 整理所有 eventType 枚举值，确保每个值都有对应 binding pattern。

#### 6. DelayTask 缺少 createdAt 字段，调度延迟不可观测

```java
// DelayTask.java — 当前字段
private String taskId;
private String taskType;
private long executeAt;
private Map<String, Object> payload;
// 无 createdAt
```

入队时间缺失，无法计算任务在队列中的实际等待时长，也无法区分"刚入队"和"已经延误很久"的任务，影响监控和告警。

建议：增加 `private long createdAt;`，在 `RedisDelayTaskPublisher.publish` 时设置为当前时间戳。消费时记录 `actualDelay = System.currentTimeMillis() - task.getCreatedAt()` 以便监控。

#### 7. delayExchange 声明为普通 TopicExchange，与名称语义不符

```java
// RabbitMqConfig.java（估算）
@Bean
public TopicExchange delayExchange() {
    return new TopicExchange(EXCHANGE_DELAY, true, false);
}
```

当前的 `delayExchange` 是一个普通 Topic exchange，消息发送后立刻路由，不提供任何延迟语义。延迟能力实际由 Redis ZSet 承担，这个 exchange 目前没有实际作用，但命名会造成误解。

建议：要么将其重命名以明确职责（例如 `EXCHANGE_SCHEDULED_NOTIFY`），要么如果确实需要 RabbitMQ 端的延迟队列，安装 `rabbitmq-delayed-message-exchange` 插件并声明：

```java
Map<String, Object> args = new HashMap<>();
args.put("x-delayed-type", "topic");
return new CustomExchange(EXCHANGE_DELAY, "x-delayed-message", true, false, args);
```

#### 8. AsyncConfig 所有线程池仍使用 CallerRunsPolicy，AI 执行器未单独配置

```java
// AsyncConfig.java:86（估算）
executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
```

对 `aiExecutor` 而言，`CallerRunsPolicy` 意味着队列满时 AI 任务在调用方线程（通常是 HTTP 请求线程或其他业务线程）上直接执行，彻底失去了线程隔离的意义，导致 AI 慢请求拖死 Web 容器线程池。

建议：`aiExecutor` 改用 `AbortPolicy` + 较小的 `queueCapacity`（建议 50~100），在服务层捕获 `RejectedExecutionException` 并返回"系统繁忙，请稍后重试"。其他执行器视业务特性决定是否保留 `CallerRunsPolicy`。

#### 9. DomainEvent 无 Lombok，9 个字段全部手写 getter/setter

```java
// DomainEvent.java
// 无 @Data / @Builder，~80 行手写 getter/setter/toString
```

维护成本高，新增字段容易漏写，序列化/反序列化测试也容易遗漏。

建议：加 `@Data @Builder @NoArgsConstructor @AllArgsConstructor`，删除手写的 getter/setter。
