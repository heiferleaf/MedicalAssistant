# 任务分工和测试文档

## 1. 文档目标

这份文档用于承接 `high-concurrency-backend-plan.md` 的落地执行，明确：

- 每一类任务由谁负责。
- 五个独立交付模块分别包含哪些需求、设计、开发和测试工作。
- 各任务的交付物是什么。
- 测试怎么做。
- 什么状态算完成。

本文档默认按后端主导、前后端联动、测试配合的方式组织。如果团队人数更少，可以由同一人兼任多个角色，但任务边界不要混。

## 2. 五个独立交付模块

本节把高并发后端改造拆成 5 个相对独立的模块。每个模块都包含需求、设计、开发、测试完整闭环，便于 5 个小组并行推进。模块之间只通过配置、接口、事件、消息和文档约定协作，避免互相等待。

工作量平衡原则：

- 每个模块约占总工作量 20%，都包含设计、编码、联调、测试和文档。
- 每个模块都能独立提交 PR、独立验收，但最终要进入统一微服务环境做集成验证。
- 基础设施类能力先定义接口和配置契约，业务模块只依赖契约，不直接依赖实现细节。
- 若团队人数不足，可以一人兼任多个模块，但不要把同一模块的需求、开发、测试责任拆散。

| 模块 | 模块名称 | 主要目标 | 工作量占比 | 主要交付 |
| --- | --- | --- | --- | --- |
| 模块一 | 基础设施与服务治理 | 配置开关、线程池、连接池、观测、熔断限流 | 约 20% | 基础设施配置、监控指标、治理能力 |
| 模块二 | 数据库与缓存优化 | 索引、批量 SQL、热点缓存、防击穿 | 约 20% | SQL 优化、缓存策略、数据压测结果 |
| 模块三 | 事件总线与延迟任务 | RabbitMQ 事件、幂等、死信、Redis 延迟任务 | 约 20% | 事件模型、延迟任务平台、消费保障 |
| 模块四 | WebSocket 通知与网关多实例 | 跨实例推送、在线路由、通知服务、Nginx 动态解析 | 约 20% | notification 能力、推送链路、多实例验证 |
| 模块五 | Agent / AI 性能与会话治理 | Agent/RAG/OCR/Predict 提速、异步化、会话共享 | 约 20% | AI 调用治理、缓存、异步任务、会话连续性 |

### 2.1 模块一：基础设施与服务治理

模块边界：

- 负责所有模块共用的运行时底座，不直接改业务语义。
- 输出统一配置、线程池、连接池、HTTP client、观测、熔断限流能力。
- 不负责具体 Agent 业务逻辑、不负责具体 SQL 改写、不负责 WebSocket 业务推送语义。

#### 需求

- 所有基础设施能力必须显式开关，避免默认启用导致多实例重复消费或重复调度。
- Tomcat、Hikari、Redis、外部 HTTP client 都要有可调配置和可观测指标。
- `aiExecutor`、`wsPushExecutor`、`domainEventExecutor`、`pdfExecutor` 独立隔离。
- 生产 profile 不使用 MyBatis `StdOutImpl` 输出 SQL。
- 外部依赖调用要具备超时、限流、熔断、bulkhead 和降级入口。

#### 设计

- 建立服务能力矩阵，明确 user / medication / family / health / agent / notification / scheduler 各 profile 的启用能力。
- 在 `common/infra/async` 收口线程池配置，统一 MDC 传播和拒绝策略。
- 在 `common/infra/resilience` 或配置层统一 Resilience4j 策略。
- 在 `common/infra/observability` 暴露线程池、MQ、延迟任务、HTTP client 指标。
- 统一外部 HTTP client 抽象，供 Agent/OCR/RAG/Predict 模块接入。

#### 开发

- 修改所有基础设施组件的 `@ConditionalOnProperty`，取消隐式 `matchIfMissing = true`。
- 补齐 `application-*.yaml` 中各 profile 的显式能力开关。
- 增加 Tomcat、Hikari、Redis pool 参数配置。
- 实现命名线程池和任务装饰器。
- 接入 Actuator / Micrometer，自定义线程池、MQ、延迟任务指标。
- 提供统一 HTTP client Bean，带连接池、超时和指标。

#### 测试

- 单体模式和微服务模式分别执行 compose config 校验。
- 启动各 profile，核对启动日志中的能力清单。
- 压测下观察 Tomcat、Hikari、Redis、线程池指标是否可见。
- 模拟 AI 线程池满载，验证返回受控错误而不是拖垮 Web 线程。
- 验证生产配置不输出 SQL stdout。

#### 交付物和验收

- 服务能力矩阵。
- 配置参数清单。
- 线程池和连接池指标说明。
- 外部 HTTP client 使用说明。
- 验收标准：基础设施能力显式可控，压测时能定位 Web、DB、Redis、线程池、外部 HTTP 哪一层成为瓶颈。

### 2.2 模块二：数据库与缓存优化

模块边界：

- 负责 MySQL 查询性能、索引、N+1 消除、Redis 缓存策略。
- 不负责 MQ 消费框架，不负责 WebSocket 发送，不负责 Agent 编排。
- 对外输出稳定 Mapper / Service 查询能力和缓存接口。

#### 需求

- 修复 mapper 与建表脚本不一致问题，压测前保证数据正确。
- 为任务、药品、家庭成员、健康数据、家庭事件日志补齐组合索引。
- 消除药品、家庭健康快照、Agent session 列表等 N+1 查询。
- 热点缓存要具备随机 TTL、空值缓存、互斥重建或逻辑过期。
- 缓存失效要能被业务事件或 Canal 兜底机制触发。

#### 设计

- 按真实访问模式设计索引，而不是只按单字段建索引。
- 为 `MedicineMapper`、`MedicationTaskMapper`、`HealthDataMapper`、Agent session 查询增加批量接口。
- 家庭健康快照采用“成员一次取、健康数据一次取、任务统计一次取”的聚合方案。
- Redis 缓存封装统一支持空值、随机 TTL、互斥锁和指标埋点。
- 变更前后保留 explain 结果和压测指标。

#### 开发

- 修正 `FamilyEventLogMapper.findDailyAlarms` 表名和字段名。
- 更新 `docker/init.sql` 或 migration，补齐组合索引。
- 增加 `findByIds`、`findLatestByUserIds`、`countByUsersAndDate` 等批量 Mapper。
- 改造 `PlanServiceImpl.getPlanList`、`TaskServiceImpl.batchQueryMedicines`、家庭健康快照、Agent session 列表查询。
- 为热点缓存增加随机 TTL、空值缓存和击穿保护。
- 补充缓存命中、回源、重建失败等指标。

#### 测试

- 对每个热点 SQL 执行 explain，记录是否命中预期索引。
- 构造家庭组、任务、药品、健康数据规模化数据，验证接口结果一致。
- 压测今日任务、药品列表、家庭健康快照、家庭告警。
- 模拟缓存同时过期，验证没有大量请求直接打穿 DB。
- 验证缓存失效后能正确回源并重建。

#### 交付物和验收

- 索引变更清单。
- SQL 优化前后 explain 对比。
- N+1 查询替换说明。
- 缓存键、TTL、失效策略说明。
- 验收标准：核心查询接口 DB QPS 和 P95 明显下降，热点缓存命中率可观测并达到压测目标。

### 2.3 模块三：事件总线与延迟任务

模块边界：

- 负责领域事件模型、RabbitMQ 拓扑、幂等消费、重试死信、延迟任务平台。
- 不负责具体 WebSocket session 管理，不负责具体业务 SQL 优化。
- 对业务模块暴露事件发布和延迟任务发布接口。

#### 需求

- 业务 Service 不直接执行推送、短信、缓存刷新等副作用。
- 任务状态变更、家庭成员变更、健康数据变更至少三类事件走统一事件模型。
- RabbitMQ 要包含 domain exchange、delay exchange、DLX。
- 消费者必须有幂等、重试、失败日志和死信处理。
- 服药提醒、漏服标记、家庭邀请过期不再依赖单 JVM `ScheduledFuture`。

#### 设计

- 定义统一 `DomainEvent`：`eventId`、`eventType`、`aggregateType`、`aggregateId`、`userId`、`groupId`、`occurredAt`、`traceId`、`payload`。
- RabbitMQ 按 domain、delay、dead-letter 三层拓扑设计。
- Hook 执行策略采用“事务提交后异步执行”，每个 hook 使用 `eventId + hookName` 幂等。
- 延迟任务短期使用 Redis ZSet，score 为执行时间戳，Lua 原子抢占。
- 失败任务按 retryCount 退避重试，耗尽后进入死信或补偿清单。

#### 开发

- 新增或完善 `common/infra/event`、`common/infra/mq`、`common/infra/idempotency`、`common/infra/delay`。
- 抽出 `DelayTask`、`DelayTaskPublisher`、`DelayTaskConsumer`、`DelayTaskHandler`。
- 将服药提醒、漏服标记、家庭邀请过期迁移到统一延迟任务。
- 为 MQ 消费和延迟任务消费增加幂等键。
- 建立 DLX 队列和失败日志。
- 保留旧 scheduler 开关，迁移完成后默认关闭。

#### 测试

- 单实例验证事件发布、消费、重试、死信。
- 两个 scheduler 实例并发消费同一批延迟任务，验证每个任务只执行一次。
- 模拟消费者异常，验证 retryCount 增加并最终进入死信。
- 停止 RabbitMQ 后恢复，验证业务主流程和消息补偿策略。
- 压测同一时间点大量提醒任务，观察积压和恢复速度。

#### 交付物和验收

- 事件模型文档。
- RabbitMQ 拓扑说明。
- 延迟任务设计和迁移说明。
- 幂等、重试、死信处理说明。
- 验收标准：多实例下不重复提醒、不漏处理任务，消息积压和失败可观测可补偿。

### 2.4 模块四：WebSocket 通知与网关多实例

模块边界：

- 负责 WebSocket 连接、在线路由、跨实例推送、notification-service、Nginx/gateway 多实例适配。
- 不负责业务事件生产，只消费推送命令。
- 不负责 Agent 推理本身，只负责通知和结果送达。

#### 需求

- WebSocket session 不能只保存单 JVM 单 session。
- 同一用户多端在线时所有连接都能收到消息。
- 任意业务实例发布推送事件，用户实际连接的 notification 实例都能发送。
- 只有 notification-service 消费 `queue.ws.push`。
- 容器重建后 Nginx 不应长期缓存旧 upstream IP 导致 502。
- 短信、站内通知等非 WebSocket 通知要有 hook 扩展点。

#### 设计

- `WebSocketSessionManager` 改为 `userId -> sessionId set` 和 `sessionId -> session`。
- Redis 维护 `ws:route:user:{userId} -> instanceId`，并设置 TTL。
- 每个 notification 实例订阅自己的节点通道，或统一消费 `queue.ws.push` 后按路由转发。
- 推送命令统一使用 `WsPushCommand`，payload 只保留结构化 Map。
- Nginx 使用 Docker DNS 动态解析服务名，避免容器重建后的旧 IP 问题。
- 通知类 hook 与 WebSocket 发送解耦，短信网关未接入时保留可替换实现点。

#### 开发

- 改造 `WebSocketSessionManager` 支持多端连接和会话清理。
- 实现在线状态 TTL、心跳续期和异常断线清理。
- 确保 `WsPushMessageListener` 只在 notification profile 显式启用。
- 完善 `ApplicationEventWsPushBridge`、`WsPushPublisher`、`WsPushCommand`、推送消费者。
- 增加短信通知 hook，例如家庭服药告警 owner 手机号通知路径。
- 修改 `nginx.microservices.conf`，使用动态 resolver 和变量 `proxy_pass`。

#### 测试

- 单用户单端、单用户多端、多人家庭组推送测试。
- 两个 notification 实例下，用户连接 A，业务事件从 B 或其他服务触发，验证送达 A。
- 重启一个 notification 实例，验证其他实例连接不受影响，断线用户重连后路由恢复。
- RabbitMQ 中检查 `queue.ws.push` consumer 数只等于 notification listener 并发。
- 重建 user/family/agent 容器后，通过 Nginx 验证不出现持续 502。

#### 交付物和验收

- WebSocket 路由设计文档。
- notification-service 职责说明。
- Nginx 动态解析配置说明。
- 多实例推送联调报告。
- 验收标准：跨实例推送成功、多端送达、无重复推送、容器重建后路由自动恢复。

### 2.5 模块五：Agent / AI 性能与会话治理

模块边界：

- 负责 Agent、RAG、OCR、Predict 的性能治理、缓存、异步任务和会话连续性。
- 使用模块一提供的统一 HTTP client 和线程池，不重复建设基础设施。
- 不负责核心任务/家庭/健康业务 SQL 优化。

#### 需求

- AI 慢请求不能占满核心 Web 请求线程。
- `OcrService`、`RagService`、`PredictService` 不再各自 `new RestTemplate()`。
- `PredictService` 不再硬编码 `localhost`，统一走 `${flask.base-url}`。
- Agent 短请求和复杂长请求分级处理。
- RAG / OCR / Predict 重复请求可缓存。
- Agent 会话上下文要支持跨实例连续，不能只依赖单机内存窗口和 `ThreadLocal`。

#### 设计

- 所有 Flask / OCR / RAG / Predict 调用接入统一 HTTP client。
- Agent 请求分为轻量同步和复杂异步两类：复杂请求返回 `taskId`，结果通过轮询或 WebSocket 返回。
- RAG 缓存 key 使用 `question + topK + strategy` hash，OCR 使用图片内容 hash，Predict 使用规范化 JSON hash。
- Agent memory 使用数据库或 Redis-backed `ChatMemoryStore`，memoryId 与 sessionId 对齐。
- 工具执行上下文显式传递 sessionId / traceId，避免跨线程后 `ThreadLocal` 丢失。

#### 开发

- 改造 `OcrService`、`RagService`、`PredictService` 使用统一 HTTP client。
- 将 Predict 地址配置化。
- 将 SSE / 复杂 Agent 执行切到 `aiExecutor`。
- 增加 RAG / OCR / Predict 缓存和缓存预热入口。
- 增加 Agent 异步任务表或 Redis 状态，支持 taskId 查询。
- 替换或封装 LangChain4j 单机 memory，统一历史消息裁剪逻辑。
- LLM key 缺失或外部 Flask 不可用时返回明确降级结果。

#### 测试

- Agent health、普通 chat、SSE chat、RAG、OCR、Predict 功能回归。
- 未配置 `DASHSCOPE_API_KEY` 时验证 agent-service 不崩溃，接口返回明确提示。
- 重复 RAG/OCR/Predict 请求验证缓存命中和耗时下降。
- 并发复杂 Agent 请求验证 `aiExecutor` 队列、拒绝、降级可观测。
- 同一 session 请求打到不同 agent 实例，验证上下文连续。
- 模拟 Flask 超时或不可用，验证核心业务接口不受明显影响。

#### 交付物和验收

- AI 调用链路图。
- Agent 请求分级规则。
- 缓存键与 TTL 设计。
- 异步 taskId 协议说明。
- AI 压测报告。
- 验收标准：简单 Agent 问答、缓存命中 RAG、OCR/Predict 达到阶段指标，AI 故障不拖垮核心业务。

### 2.6 模块间接口和协作约定

| 提供方 | 使用方 | 契约 | 说明 |
| --- | --- | --- | --- |
| 模块一 | 全部模块 | profile 开关、线程池、HTTP client、指标接口 | 其他模块不得私自创建公共线程池或零散 HTTP client |
| 模块二 | 模块三、四、五 | 批量 Mapper、缓存接口、缓存失效策略 | 事件和推送只调用稳定接口，不跨包访问实现细节 |
| 模块三 | 模块四、五 | `DomainEvent`、`DelayTask`、MQ 拓扑、幂等服务 | WebSocket 和 AI 异步结果通过事件或消息解耦 |
| 模块四 | 模块三、五 | `WsPushCommand`、notification 推送入口 | 业务和 Agent 只发布推送命令，不直接拿本地 session |
| 模块五 | 模块一、三、四 | AI task 状态、结果事件、推送通知 | AI 长任务结束后通过事件和 WebSocket 返回结果 |

集成顺序建议：

1. 模块一先交付最小基础设施契约：配置、线程池、HTTP client、指标。
2. 模块三基于模块一交付事件和延迟任务最小闭环。
3. 模块四基于模块三接入 `WsPushCommand`，完成 notification 独占消费。
4. 模块二可并行做 SQL 和缓存优化，只需遵守事件失效契约。
5. 模块五最后接入统一 HTTP client、AI 线程池、taskId 和 WebSocket 结果推送。

## 3. 角色视角任务分工建议

### 3.1 基础设施组

负责范围：

- Spring Boot profile 与基础设施开关收口。
- 统一 HTTP 客户端。
- 线程池治理。
- Actuator / Micrometer / 监控指标。
- Resilience4j / 超时 / 限流 / 熔断。

具体任务：

1. 梳理所有 `@ConditionalOnProperty` 默认行为，取消 `matchIfMissing = true` 的隐式启用。
2. 统一 Flask / OCR / RAG / Predict 的 HTTP 客户端实现。
3. 配置连接池、超时、重试、bulkhead、限流。
4. 增加线程池监控指标、MQ 指标、延迟任务指标。
5. 下线 `StdOutImpl` SQL 日志，补齐生产配置。

交付物：

- 配置清单。
- 基础设施能力矩阵。
- 指标面板说明。
- 压测前环境参数模板。

### 3.2 分布式架构组

负责范围：

- WebSocket 跨实例路由。
- 延迟任务平台化。
- 在线状态和实例路由状态共享。
- Agent 会话共享状态。

具体任务：

1. 改造 `WebSocketSessionManager` 为多 session 模型。
2. 落地 `userId -> instanceId` 路由表和 TTL 心跳。
3. 实现 ws 推送命令的 Redis / RabbitMQ 分发。
4. 将 `DynamicTaskScheduler` 迁移到 Redis ZSet 或 MySQL delay task。
5. 为任务消费增加幂等、重试、死信。
6. 统一 Agent session memory，移除单机内存窗口依赖。
7. 去掉工具执行链上对 `ThreadLocal` 上下文的强依赖。

交付物：

- 分布式时序图。
- WebSocket 路由方案文档。
- 延迟任务设计文档。
- 幂等和失败补偿说明。

### 3.3 Agent / AI 组

负责范围：

- Agent / RAG / OCR / Predict 提速。
- 同步和异步调用分级。
- 缓存与预热。
- 工具链收敛。

具体任务：

1. 移除 `OcrService`、`RagService`、`PredictService` 里的零散 `new RestTemplate()`。
2. 统一接入带连接池的客户端。
3. 将 `PredictService` 的硬编码地址改为配置化。

## 4. 分阶段任务排期建议

### 第一阶段：压测前修正

目标：先保证系统行为正确，避免在错误实现上做性能优化。

任务：

- 修正 mapper / 表字段不一致问题。
- 修正延迟任务调度中的明显正确性问题。
- 收口基础设施开关。
- 去掉生产 stdout SQL 日志。
- 接入基础监控。

完成标准：

- 单实例功能稳定。
- 基础指标能看。
- 配置职责清晰。
- 压测脚本能跑通，并形成第一份基线报告。
- P0 正确性问题全部关闭，不再带已知逻辑错误进入压测。

阶段门禁：

- `docker compose` 单体模式和微服务模式配置都能通过 config 校验。
- 关键 API 回归通过：登录、今日任务、创建计划、任务状态更新、家庭快照、Agent health。
- 生产 profile 不输出 MyBatis SQL 到 stdout。
- 所有基础设施开关都有显式配置项和默认策略说明。

### 第二阶段：连接池与线程池治理

目标：提升稳定性，避免线程和连接被慢调用拖死。

任务：

- 统一 HTTP 客户端。
- 配置 Hikari / Redis / Tomcat。
- 增加专用 aiExecutor / wsPushExecutor / domainEventExecutor / pdfExecutor。
- 给 AI 调用加并发隔离。

完成标准：

- 高并发下不会因为默认线程池或默认连接池直接雪崩。
- AI 慢调用和核心业务线程分离。
- Tomcat、Hikari、Redis、外部 HTTP client 的连接池参数可观测、可调优。
- AI 线程池满载时表现为受控拒绝或排队，不拖垮 Web 请求线程。

阶段门禁：

- Hikari 连接池等待时间接近 0，压测期间无明显连接泄漏。
- Redis pool 无长时间等待，慢命令可定位。
- 外部 HTTP 调用有 connect/read timeout、最大连接数、失败率指标。
- `aiExecutor`、`wsPushExecutor`、`domainEventExecutor`、`pdfExecutor` 队列长度和拒绝次数可查看。

### 第三阶段：数据与缓存优化

目标：先把热点读和 N+1 压下来。

任务：

- 建组合索引。
- 改批量查询。
- 做热点缓存。
- 为 Agent / RAG / OCR / Predict 增加缓存。

完成标准：

- 查询型接口数据库压力明显下降。
- 重复 AI 请求可命中缓存。
- 热点缓存具备随机 TTL 和空值缓存策略。
- 主要查询有 explain 结果和索引命中说明。

阶段门禁：

- `PlanServiceImpl.getPlanList`、`TaskServiceImpl.batchQueryMedicines` 不再逐 ID 查询药品。
- 家庭健康快照不再按家庭成员循环查最近健康数据和今日任务统计。
- Agent session 列表不再逐 session 查询最后消息。
- Redis 缓存命中率、回源次数、空值缓存命中数有统计口径。

### 第四阶段：分布式底座改造

目标：让系统具备真正的多实例运行能力。

任务：

- WebSocket 路由共享。
- 延迟任务平台化。
- Agent session 状态共享。
- 任务消费幂等、重试、死信。

完成标准：

- 多实例部署下不重复提醒、不漏推送、不丢会话。
- 容器重建、单实例重启、消息积压恢复后系统能自动收敛。
- 推送、延迟任务、领域事件都有幂等和失败补偿路径。

阶段门禁：

- 两个以上 scheduler 实例同时运行时，同一延迟任务只执行一次。
- 任意业务实例发布 WebSocket 推送事件，用户连接所在 notification 实例都能收到。
- 同一用户多端连接时，多端都能收到推送。
- 单个 notification 实例重启后，在线状态能通过 TTL 和重连恢复。

### 第五阶段：Agent 提速与异步化

目标：把重 AI 链路和核心业务彻底隔离。

任务：

- Agent 长请求异步化。
- 简单问答前置路由。
- 缓存预热。
- 降级策略落地。

完成标准：

- Agent 高峰不会拖慢任务、家庭、健康等核心接口。
- 简单问答、轻量 RAG、复杂工具链请求有清晰分级。
- 长请求能返回 `taskId`，通过轮询或 WebSocket 获取最终结果。
- Flask / LLM 不可用时，核心业务仍能稳定返回。

阶段门禁：

- Agent 短请求 P95 与复杂异步任务分开统计。
- AI 任务排队长度、执行耗时、失败次数、降级次数可观测。
- 重复 RAG / OCR / Predict 请求可命中缓存。
- 工具执行链不依赖不可跨线程传递的隐式上下文。

建议流量配比：

| 接口类型 | 占比 | 说明 |

| 指标 | 目标 |

| 核心接口 P99 | < 500 ms |
| HTTP 5xx | < 0.1% |
| Hikari pending / wait | 接近 0 |

### 5.6 故障演练测试

## 6. 关键验收标准

### 6.1 核心业务

- 登录、任务、药品、家庭、健康核心接口保持稳定。
- 在 AI 高峰或外部依赖抖动时，核心业务不被明显拖慢。

### 6.2 分布式能力

- WebSocket 推送支持跨实例路由。
- 延迟任务支持多实例唯一消费。
- Agent 会话支持跨实例连续。
- 所有基础设施能力通过显式配置启用。

### 6.3 Agent 提速

- 简单 Agent 问答响应明显快于完整工具链请求。
- 重复 RAG / OCR / Predict 请求可命中缓存。
- AI 重请求可异步化，不阻塞主业务链路。

### 6.4 可观测性

- 能看到线程池、连接池、MQ、延迟任务、外部 HTTP 调用的核心指标。
- 能区分问题出在 Web 层、DB、Redis、MQ、Flask 还是 LLM。

### 6.5 总体验收门禁

以下条件全部满足后，才算高并发后端改造阶段性可交付：

| 类别 | 门禁 |
| --- | --- |
| 正确性 | P0 正确性问题全部修复；核心 API 回归通过；重复请求具备幂等保护 |
| 配置 | 所有基础设施能力显式开关；各 profile 职责清晰；配置矩阵与实际启动日志一致 |
| 性能 | 核心业务 P95 / P99 达到阶段目标；AI 场景单独统计且不拖慢核心业务 |
| 数据库 | 主要热点 SQL 有索引和 explain 记录；N+1 查询已替换或有明确延期说明 |
| 缓存 | 热点缓存有随机 TTL、空值缓存、击穿保护；缓存失效链路可验证 |
| MQ | 队列、重试、死信、幂等、积压指标可验证；异常恢复后消息可自动消费 |
| WebSocket | 支持跨实例推送、多端推送、断线重连；路由状态有 TTL |
| 延迟任务 | 多实例唯一消费；失败可重试；重试耗尽进入死信或补偿清单 |
| Agent | 外部 HTTP client 统一；长请求异步化或隔离；LLM/Flask 不可用时有降级 |
| 观测 | 指标、日志、traceId 能支撑定位瓶颈；压测报告包含资源和业务指标 |
| 运维 | 上线步骤、回滚步骤、故障演练记录齐全 |

### 6.6 回滚要求

每个阶段上线前都要准备回滚方案：

- 配置类改动：保留上一版配置文件和环境变量快照，可快速恢复。
- MQ / 延迟任务改动：保留旧消费者关闭开关，新消费者异常时能暂停消费并保留消息。
- WebSocket 改动：保留旧推送路径开关，跨实例路由异常时能降级为单实例 sticky session。
- 数据库索引改动：DDL 使用低峰执行，记录执行耗时；大表变更需要提前评估锁表风险。
- Agent 改动：AI 异步任务可降级为“排队中/系统繁忙”，不能影响核心业务接口。
- Nginx / 网关改动：修改前备份配置，`nginx -t` 通过后再 reload。
