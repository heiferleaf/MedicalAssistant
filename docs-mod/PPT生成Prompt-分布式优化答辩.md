### P6 — 单体架构四大痛点【问题分析 · 重点】

- **一页一重点**：单体在性能/可用/可靠/扩展四个维度的系统性缺陷
- **内容（2×2 象限或四列表）**：
  - 性能：AI/OCR/RAG 慢调用占用 Web 线程，拖慢核心接口；N+1 查询（药品循环、家庭快照、session 列表）；缺组合索引
  - 可用性：WebSocket 连接存单机内存，单点不可用即断推送
  - 可靠性：ApplicationEvent 仅进程内传播，事务回滚后仍误推；MQ routing key 不匹配静默丢消息；WebSocket sendMessage 非线程安全
  - 可扩展性：HTTP 有状态难水平扩展；跨 Mapper 调用难拆分；Nginx 缓存旧容器 IP 致持续 502
- **设计**：2×2 象限图，每象限一个图标 + 2 条短句。用红色标注「痛点」

### P7 — 分布式化的核心挑战【问题分析 · 重点】

- **一页一重点**：拆分本身会引入的新问题（为下一章技术方案铺垫）
- **内容（痛点 → 影响）**：
  - 事件跨进程：进程内事件无法跨容器 → 需可靠消息中间件
  - 状态外置：WebSocket 路由 / 会话 / 幂等状态需迁出本机内存
  - 重复执行：本机定时任务多实例下重复或丢失
  - 数据一致性：缓存与 DB 一致性、事务与事件一致性
  - 消息可靠性：发布丢失、消费丢失、无重试兜底
- **设计**：左「单体做法」右「分布式要求」的对照箭头图；强调「拆分不是免费的」
- **演讲提示**：引出"我们如何在低复杂度下解决这些挑战"

### P8 — 大模型 / RAG 链路瓶颈【问题分析 · 重点】

- **一页一重点**：AI 链路是性能大头，且藏着一个被缓存掩盖的并发 bug
- **内容**：
  - 瓶颈占比：真实 API 下 **LLM 调用占 Chat 总耗时 90%+**，本地管道仅 <10%（S1: 本地 1342ms vs 真实 17758ms）
  - 隐藏 bug：Flask AI 端点 `async def` + 同步阻塞 SDK → 单 worker 下并发被迫串行，吞吐卡死 0.2 req/s
  - 为何没早发现：原 benchmark 经 Spring 缓存层 + 重复问题 → 100% 缓存命中（5.8ms），并发请求从未真正打到 Flask
- **设计**：饼图（LLM 90% vs 管道 10%）+ 一条「缓存掩盖 bug」的示意图。突出反差
- **演讲提示**：强调"分层压测"的方法论价值

### P9 — 为什么这样拆（拆分依据）【技术方案 · 重点 · 要有理由】

- **一页一重点**：拆分有依据，选型做减法
- **内容（两栏）**：
  - 左·拆分依据（边界划分）：按「核心业务短路径」隔离——登录/任务/药品/家庭/健康 不被 AI/PDF/推送/延迟任务拖慢；WebSocket 只由 notification-service 维护；延迟任务只由 scheduler-service 消费；Service 只发事件不做副作用
  - 右·选型做减法（为什么不用）：
    - 不用 Nacos：模块化单体下 Nginx 静态路由足够，避免运维复杂度
    - 不用 Seata：共享库 + 本地事务足够，无需分布式事务
    - 不拆库：当前数据量无需分库，避免跨库查询复杂度
    - 不用 OpenFeign：保留直接调用，性能更优、调试方便
- **设计**：左「拆分原则」清单 + 右「技术选型取舍表（方案 / 为什么不用）」。这页体现工程判断力，是答辩加分点

### P10 — 事件驱动 + 消息可靠性【技术方案】

- **一页一重点**：用 RabbitMQ 领域事件解耦，三重保障消息不丢
- **内容**：
  - 事件驱动（U1）：ApplicationEvent → RabbitMQ DomainEvent；交换机 `medical.domain.topic` / `medical.delay.topic` / `medical.dlx.topic`；事件在「事务提交后」发布，避免回滚误推
  - 消息可靠性（U5）：Publisher Confirm + Returns（发布确认）→ Consumer Manual ACK（消费确认）→ DLQ 死信兜底（重试 3 次后入队）
  - 效果：消息「可能丢失 → 不丢失」，代价仅 1-5ms
- **设计**：生产者→交换机→队列→消费者的消息流图，在三个环节标注「Confirm / ACK / DLQ」三道关卡
- **数据点**：已配置 7 个 DLQ 队列；6 项可靠性测试全通过

### P11 — 延迟任务可靠性 U6【技术方案 · 重点】

- **一页一重点**：延迟任务从「重启即丢」升级为「持久化 + 不重复 + 可重试」
- **内容（改进前 → 改进后对照表）**：
  | 维度 | 改进前 | 改进后 |
  |------|--------|--------|
  | 存储 | JVM 堆 ConcurrentHashMap | Redis ZSET (`infra:delay:tasks`) |
  | 重启恢复 | 重扫 DB，精度按天 | 持久化，毫秒级恢复 |
  | 多实例 | 重复执行 | Lua 原子 POP（ZRANGEBYSCORE+ZREM）不重复 |
  | 失败重试 | 无，失败即丢 | 指数退避 2s→4s→8s，最多 3 次 |
  | 重试耗尽 | 静默丢弃 | 投递 DLQ，可追溯重发 |
  | 可见性 | 无 | 监控 API + Actuator |
- **设计**：左 Redis ZSET + Lua 抢占示意图，右改进前后对照表。任务类型标注（服药提醒/漏服/邀请过期）
- **数据点**：轮询间隔 1s，每次最多弹 100 条

### P12 — 服务治理与可观测【技术方案】

- **一页一重点**：限流、分布式锁、链路追踪三件套保障稳定与可观测
- **内容（三栏）**：
  - 限流降级（U3 Sentinel）：`/api/agent/chat/stream` 10 QPS、`/api/ocr/*` 5 QPS、`/api/agent/chat` 并发 20；压测时可调高至 2000 测真实瓶颈
  - 分布式锁（U2 Redisson）：`@DistributedLock(key="#taskId")` AOP + SpEL；用药状态更新、家庭操作、AI 工具加锁
  - 链路追踪（U4）：Micrometer Tracing + Brave 5.16 + Zipkin（非 Sleuth，已弃用）；traceId 全链路注入日志 MDC；采样开发 100%/生产 10%；开销 <5%
- **设计**：三列卡片，每列一个图标 + 关键参数。底部放一张 Zipkin 链路 trace 示意图

### P13 — 大模型 / RAG 优化与迭代历程【技术方案 · 重点 · 演变迭代】

- **一页一重点**：AI 链路的多轮迭代优化（讲"演进故事"）
- **内容（时间轴/迭代箭头，体现 history）**：
  1. 可靠性：三层 LLM 回退（MedicalAgent → StreamingChatModel → 阻塞 ChatModel）+ 空响应重试
  2. 弹性：Resilience4j 三层保护（Retry 3 次 → RateLimiter 20/s → CircuitBreaker 50% 失败率熔断）
  3. 省钱：ChatCacheService（MD5 缓存键，短文本 TTL 300s）
  4. 性能：aiExecutor 线程池 8→20→50/200，HTTP 状态码修复（429/504 不再伪装 200）
  5. RAG 治理：统一 AiHttpClient 连接池、Redis 缓存（TTL 抖动+空值缓存+Redisson 锁防击穿）、bulkhead 限流
  6. 并发修复（最新）：Flask `async def`→`def`，10 并发吞吐 0.2→1.06 req/s（5.3×）
- **设计**：横向迭代时间轴，6 个节点，每节点一句话 + 一个小指标。右下角放并发修复前后柱状对比
- **演讲提示**：强调"问题驱动的持续迭代"，这是 AI 侧的核心叙事
