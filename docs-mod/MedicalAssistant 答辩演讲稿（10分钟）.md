## P1 — 封面（18s）

各位老师好，我是 XXX。我们团队的项目是 **MedicalAssistant 智能医疗助手**。

我们的主线是：**从单体到分布式、再到大模型链路治理**——把一个 Spring Boot 单体应用，重构为高并发、高可靠的分布式系统。今天我从**软件功能、问题分析、技术方案、测试评估**四个部分汇报。

## P2 — 汇报大纲目录（12s）

整个汇报分四块：**一、软件功能**，介绍系统能力和架构演进；**二、问题分析**，单体痛点和分布式挑战；**三、技术方案**，我们如何逐个解决；**四、测试评估**，用数据验证效果。

## P3 — 系统核心功能总览（42s）

先看系统能做什么。MedicalAssistant 面向家庭场景，覆盖**四大功能模块**：

**用户与家庭**：注册登录、家庭组、成员邀请审批、权限分层——一个家庭里不同角色看到不同的健康数据。

**用药管理**，这是业务核心：建药箱、定用药计划、系统**每天自动生成用药任务**、打卡、漏服检测，形成完整的用药闭环。比如一个十天、每天两次的计划，会自动生成二十条任务。

**健康监测**：录入血压血糖，做趋势分析，子女随时看到父母的健康快照。

**AI 助手**：基于大模型提供对话问答，包括 **RAG 知识问答、药品说明书 OCR 识别、不良反应预测**。

---

## P4 — 架构演进：从单体到微服务（48s）

这页是我们工作的起点和路径。

**最初是典型的 Spring Boot 单体**——所有模块挤在一个 JVM 里，共享线程池，资源竞争严重。

我们没有一步到位，而是**渐进式演进**：先做**模块化单体**——引入事件驱动、把状态外置到 Redis、用 Profile 开关按领域边界拆分，再用 Nginx 做网关路由。

最终形成下方这张图的**七个微服务**：用户、用药、家庭、健康、Agent、通知、调度，分别对应 8081 到 8087 端口，**Nginx 按路径前缀分发**——比如 `/api/user` 走用户服务，`/api/agent` 走 Agent 服务。每个服务可以独立部署、独立扩缩容，底层共享 MySQL、Redis、RabbitMQ。

## P5 — 性能与可靠性体验亮点（28s）

先用四个数字把成果亮出来：

第一，**前序链路吞吐提升 82.6 倍**，从 8 到 661 请求每秒；第二，**500 并发下 100% 成功率**，零网关报错；第三，**RAG 并发吞吐提升 5.3 倍**；第四，**消息和延迟任务零丢失**。

一句话——**分布式架构彻底解决了单体时代的系统性瓶颈**。这些数字怎么来的，后面逐一展开。

---

## P6 — 单体架构四大痛点分析（45s）

进入问题分析。单体时代我们遇到四类痛点。

**第一，性能瓶颈突出**：AI、OCR 这类慢调用**长期占用 Web 线程池**，加上频繁的 N+1 查询，把核心接口一起拖慢。

**第二，可用性存在短板**：WebSocket 连接**存在单机内存里**，单点故障推送就断，而且没法水平扩展。

**第三，可靠性水平较低**：进程内的事件和延迟任务**没有重试机制**，关键业务消息可能静默丢失。

**第四是可扩展性**：HTTP 服务有状态、跨模块直接调 Mapper，导致后续根本拆不动。正是这第四点，逼着我们走向拆分。

---

## P7 — 分布式化的核心挑战（45s）

但是——**拆分不是免费的**。拆成分布式后，很多单体里理所当然的做法都要重做。

看这张对照表：左边是**单体旧惯例**——进程内事件、本机内存状态、本机定时任务、本地事务无脑强一致；右边是拆开后的**分布式新约束**——需要**可靠消息中间件 RabbitMQ** 跨进程传播事件、状态要**迁到 Redis**、需要调度器和分布式缓存协作保证任务可靠执行、还要保障**幂等和最终一致性**。

底下这行是核心：**数据和消息一致性是重中之重**，必须防止消息发布丢失、消费丢失、以及失败之后无人兜底。这正是我们技术方案要解决的。

---

## P8 — 大模型 / RAG 链路瓶颈分析（48s）

这里有个很有价值的发现。

先看左边的柱状图：我们把 Chat 请求的耗时拆开，发现**真实链路里 LLM 调用占了 90% 以上**——S1、S2、S3 三个场景分别是 92%、90%、91%，本地管道不到 10%。也就是说，优化重点必须放在 AI 链路。

更关键的是右边——我们压测 RAG 接口时发现一个**隐藏的并发 Bug**：Flask 用了异步端点，但内部调用 SDK 是同步阻塞的，**导致并发被迫串行**。而且更隐蔽的是：**之前的基准测试因为 100% 命中缓存，5 毫秒就返回了，把这个缺陷完全掩盖了**。

所以我们的结论是：**分层压测，是发现长链路隐蔽缺陷的唯一手段**——端到端和直调 provider 都得测。

---

## P9 — 架构拆分依据与技术取舍（45s）

进入技术方案。拆微服务，我们坚持**有理有据**。

左边是**边界划分原则**：**隔离核心业务**，让登录、健康不被 AI、PDF 的慢调用拖慢；**WebSocket 单独由 notification 服务维护**，配合 RabbitMQ 做幂等和重试；**延迟任务只由调度服务消费**；业务 Service **只发事件、不做复杂副作用**。

右边更能体现判断力——**选型做减法**：我们**没用 Nacos**，因为模块化单体下 Nginx 静态路由已经够，引入注册中心只会增加运维复杂度；**没拆库**，当前数据量无需分库，拆了反而增加跨库查询难度；**没用 OpenFeign**，保留直接调用，性能更优、调试更简单。**不为微服务而微服务**，是我们的原则。

---

## P10 — 事件消息执行三重保障（52s）

拆开之后，事件要靠 RabbitMQ 跨服务传播，那消息可靠性怎么保证？我们设计了**三重保障**。

**第一重，发布确认**：用 Publisher Confirm 和 Returns 机制，确保消息**确实送达了交换机和队列**，投递成功率提升到 99.9% 以上；路由失败也有回调，不会静默丢。

**第二重，消费确认**：启用 Consumer Manual ACK，**业务逻辑真正处理完才确认消息**，中途崩溃消息不丢，会重新投递。

**第三重，死信兜底**：配置 DLQ 死信队列，**重试三次还失败的消息自动进死信队列**，支持人工追溯排查。

这三重加起来成本只有 1 到 5 毫秒，换来的是**消息从"可能丢"变成"不丢"**。六项可靠性测试全部通过。

---

## P11 — 分布式延迟任务可靠性（42s）

第二个可靠性重点是延迟任务——比如"服药后两分钟没打卡就提醒漏服"这类场景。

看这张对照表。**改进前**用 JVM 堆内存的 Map 存任务，问题很明显：一重启全丢、多实例会重复执行、失败了直接丢弃。

**改进后**我们迁到 **Redis ZSET**，用执行时间做 Score 持久化；多实例靠 **Lua 脚本原子地执行 ZRANGEBYSCORE 加 ZREM** 来抢占，**保证同一个任务只被一个实例执行、不重复**；重启能**毫秒级精确恢复、数据零丢失**；失败则**指数退避重试**，2 秒、4 秒、8 秒，最终进死信队列。

一句话——延迟任务做到了**重启不丢、多实例不重复、失败可追溯**。

---

## P12 — 服务治理与全链路可观测（42s）

这页是服务治理和可观测性，三块。

**第一，限流降级**：用 **Sentinel** 对核心接口做限流，覆盖 `/agent/chat/stream`、`/api/ocr`、`/agent/chat` 三类入口——保障突发流量下服务不被打垮。

**第二，链路追踪**：基于 **Zipkin + Brave 5.16 + Micrometer** 构建全链路追踪。这里澄清一下，Spring Boot 3 已经弃用了 Sleuth，我们用的是官方推荐的 Micrometer Tracing。每个请求注入唯一 **TraceId**，贯穿全链路，**排查问题从"手动 grep"变成"一键关联"**。

**第三，性能开销可控**：生产环境采样率控制在 10%，**额外开销控制在 5% 以内**，平衡了可观测性和性能。

---

## P13 — 大模型 / RAG 治理优化历程（55s）

这页是 AI 侧的核心，我们做了**四轮迭代优化**。

**迭代一，可靠性**：三层 LLM 回退——优先 MedicalAgent 完整工具链，失败降级到流式，再不行用阻塞调用，配合空响应重试。

**迭代二，经济性**：ChatCacheService 基于 MD5 缓存结果，短文本缓存 300 秒，**重复请求直接走缓存，大幅省 Token**。

**迭代三，并发优化**，也是最关键的：**修复了刚才说的 Flask 并发串行 Bug**，并把 aiExecutor 线程池动态扩容到 200。

**迭代四，RAG 治理**：连接池统一、Redis 缓存加锁防击穿、Bulkhead 限流保护向量库。

效果看右边两张图：**修复前并发根本不提升吞吐、延迟随并发暴涨**；**修复后吞吐近线性增长、p50 稳定在 6 秒左右**。10 并发下，**吞吐提升 5.3 倍、p50 延迟改善 5.6 倍**。

---

## P14 — 分层多场景系统化压测方案（38s）

进入测试评估。我们的压测**分层、多场景**。

左边是**场景矩阵**：从 S1 基线 100 线程，到 S2 高并发 200、S3 长稳 150 线程跑 10 分钟、S4 毛刺 300、S5 过载 500，分别验证正常负载、性能峰值、内存稳定性、瞬时过载和降级兜底。

右边是方法论的关键——**双模式加分层**：**local-only 模式跳过 LLM**，测纯链路吞吐；**真实 API 模式调 qwen-turbo**，测全链路。同时**分层**：既测 Spring 端到端（经缓存），也测 Flask 直调（cache-miss 路径）。工具用 JMeter 加自研的 SSE 脚本测首 Token 到达时间。

---

## P15 — 量化成果对比：用数据说话（50s）

最后用数据收口。

**吞吐演进**，左上柱状图：从 Baseline 的 8，到 R2 的 431，最终 R6 的 661 ok/s。这 82.6 倍不是一步到位，而是下方阶梯图展示的——**每消除一个瓶颈就跳一个台阶**：修 nginx keepalive、放开 Sentinel 限流、扩容线程池、修复 HTTP 状态码伪装，**最终 500 并发、0 错误、666 ok/s**。

**RAG 并发修复**，右上：从 0.2 到 1.06，5.3 倍。

右边四点结论：**高可用性**——500 并发 100% 成功率；**接口覆盖**——45 个端点 93.3% 通过；**解耦代价**——我们如实呈现，微服务化让写操作增加 170 到 200 毫秒，这是 RabbitMQ 跨进程的开销，**不是性能退化，而是用可接受的延迟换服务解耦和独立部署**；**链路追踪**开销小于 5%。

---

## P16 — 总结与展望（25s）

总结一下。我们做了三件事：**第一，分布式重构**，支撑 82 倍吞吐跨越；**第二，事件驱动加 Redis 持久化**，保障可靠性；**第三，大模型长链路的深度治理和并发修复**。

未来三个方向：引入 **Outbox 模式**保障强一致、生产环境**采样率动态调优**、**多 LLM API Key 轮询**负载均衡。
