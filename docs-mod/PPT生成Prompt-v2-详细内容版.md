### P7 — 单体架构四大痛点【问题分析 · 重点】

**核心句**：单体在性能/可用/可靠/扩展四维度的系统性缺陷

**四象限（2×2，每象限图标 + 短句）**：
- **性能**：AI/OCR/RAG 慢调用占用 Web 线程，拖慢核心接口；N+1 查询（药品循环、家庭快照、session 列表）；缺组合索引
- **可用性**：WebSocket 连接存单机内存 → 单点故障即断推送
- **可靠性**：ApplicationEvent 仅进程内 → 事务回滚后仍误推；MQ routing key 不匹配静默丢消息；sendMessage 非线程安全
- **可扩展性**：HTTP 有状态难水平扩展；跨 Mapper 调用难拆分；Nginx 缓存旧容器 IP 致持续 502

**真实佐证（压测发现）**：本地压测中**并发达 5 时认证接口超时（HTTP 000，~2.7s）**——嵌入式 Tomcat + Redis 连接池瓶颈。

**配图建议**：2×2 象限图，痛点用红色标注；右下角放"5 并发即超时"的小数据点。

### P8 — 分布式化的核心挑战【问题分析 · 重点】

**核心句**：拆分本身会引入新问题（为技术方案铺垫）

**五大挑战（左"单体做法" → 右"分布式要求"对照）**：
| 挑战 | 单体做法 | 分布式要求 |
|------|---------|-----------|
| 事件跨进程 | ApplicationEvent 进程内 | 可靠消息中间件跨容器传播 |
| 状态外置 | WebSocket/会话存本机内存 | 迁出到 Redis，任意实例可处理 |
| 重复执行 | 本机定时器 | 多实例下需保证唯一消费 |
| 数据一致性 | 单库本地事务 | 缓存与 DB 一致、事务与事件一致 |
| 消息可靠 | fire-and-forget | 发布确认 + 消费确认 + 死信兜底 |

**配图建议**：左右对照箭头图，中间一条"拆分不是免费的"分隔线。

### P9 — 大模型/RAG 链路瓶颈【问题分析 · 重点】

**核心句**：AI 链路是性能大头，且藏着一个被缓存掩盖的并发 bug

**两个核心发现**：
1. **LLM 占比 90%+**：真实 API 下 Chat 总耗时中 LLM 占 90%+，本地管道 <10%
   - S1(100t)：本地 1342ms vs 真实 17758ms（LLM 占 92.4%）
2. **隐藏并发 bug**：Flask AI 端点 `async def` + 同步阻塞 SDK → 单 worker 卡死事件循环 → 并发被迫串行，吞吐卡死 0.2 req/s
   - **为何没早发现**：原 benchmark 经 Spring 缓存层 + 重复问题 → 100% 缓存命中（5.8ms），并发请求从未真正打到 Flask

**配图建议**：左饼图（LLM 90% vs 管道 10%）；右"缓存掩盖 bug"示意图（请求经缓存层直接返回，未到 Flask）。

**演讲备注**：突出"分层压测"方法论——缓存层会掩盖下游并发缺陷。

### P10 — 为什么这样拆（拆分依据）【技术方案 · 重点 · 要有理由】

**核心句**：拆分有依据，选型做减法

**左·拆分依据（边界划分原则）**：
- 按"核心业务短路径"隔离：登录/任务/药品/家庭/健康 不被 AI/PDF/推送/延迟任务拖慢
- 状态归属单一：WebSocket 连接**只由 notification-service 维护**；延迟任务**只由 scheduler-service 消费**
- 副作用外移：业务 Service **只发领域事件，不直接做推送/短信/缓存刷新**

**右·选型做减法（为什么不用，配对照表）**：
| 排除方案 | 原因 |
|---------|------|
| ❌ Nacos 注册发现 | 模块化单体下 Nginx 静态路由已够，避免运维复杂度 |
| ❌ Seata 分布式事务 | 共享库 + 本地事务足够，无需分布式事务 |
| ❌ 拆分数据库 | 当前数据量无需分库，避免跨库查询复杂度 |
| ❌ OpenFeign 跨服务调用 | 保留直接调用，性能更优、调试方便 |

**配图建议**：左"拆分原则"三条清单，右"技术选型取舍表"。这页是工程判断力的加分点。

**演讲备注**：强调"适度分布式"——不为微服务而微服务。

### P11 — U1 事件驱动改造【技术方案 · 重点 · 已完成用例】

**核心句**：进程内事件 → RabbitMQ 跨服务事件，消费端按职责解耦

**改造前后架构对比（配双框图）**：
```
【改造前·单体】                       【改造后·微服务】
业务Service                            业务Service
  │ publishEvent                         │ DomainEventPublisher
  ▼ (Spring ApplicationEvent,进程内)      ▼ (RabbitMQ medical.domain.topic,跨进程)
ApplicationEventWsPushBridge           DomainEventHookExecutor
  (唯一消费者,硬编码WS推送)               │
                                        ├→ 审计 Hook (domain_event_audit 表)
                                        ├→ 推送 Hook (WebSocket)
                                        ├→ 告警 Hook
                                        └→ 缓存失效 Hook
                                        (幂等: Redis SETNX 防重复消费)
```

**核心事件流程（时序）**：业务写库 → **事务提交后**发布 DomainEvent → RabbitMQ → HookExecutor 分发到 Hook 链（异步线程，不阻塞业务）

**改进点（精简 4 条）**：
- 事件传播：进程内 → 跨服务实例
- 消费扩展：实现 `DomainEventHook` 接口即可，**无需改发布端**
- 事件审计：`domain_event_audit` 表，全局唯一 eventId
- 幂等保证：Redis SETNX 防重复消费

**代价**：写接口 +170~200ms（RabbitMQ 跨进程往返），但 Hook 异步执行不阻塞业务。

**配图建议**：左右双架构框图（如上）+ 底部一行改进点徽标。

### P12 — U5 消息可靠性【技术方案 · 重点 · 已完成用例】

**核心句**：三道关卡保障消息从"可能丢"到"不丢"

**消息可靠性三关卡（配消息流图）**：
```
生产者 ──①Publisher Confirm+Returns──→ RabbitMQ Broker ──②Manual ACK──→ 消费者
   (确认消息到达Broker,                    (durable队列)      (处理成功才ACK,    │
    路由失败有Returns回调)                                     失败NACK)        │ 处理异常
                                                                              ▼
                                                          ③DLQ 死信队列(medical.dlx.topic)
                                                            (可人工排查/重发)
```

**改造前后对比**：
| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 消息发送 | fire-and-forget 不确认 | Confirm + Returns 确认到达 |
| 消费 ACK | AUTO（投递即确认，失败丢失） | Manual（处理成功才确认） |
| 异常处理 | CanalCacheConsumer 吞异常 | 抛出 → 重试 → DLQ |
| 消息可靠性 | 可能丢失 | **不丢失** |

**测试验证（6 项全通过 ✅）**：Confirm 回调、Returns 回调、Manual ACK、NACK+DLQ、异常处理、应用启动。

**代价**：确认回调 + 手动 ACK 约 **1-5ms** 开销，换消息不丢。

**配图建议**：横向消息流图（三关卡高亮）+ 右侧 6 项验证勾选清单。

### P13 — U6 延迟任务可靠性【技术方案 · 重点 · 已完成用例】

**核心句**：延迟任务从"重启即丢"升级为"持久化 + 不重复 + 可重试"

**核心机制（配 Redis ZSET 抢占流程图）**：
```
任务入队: ZADD infra:delay:tasks  score=executeAt(毫秒时间戳)
                  │
轮询(每1秒,batch≤100):
   Lua 脚本原子执行 ZRANGEBYSCORE + ZREM  ←── 多实例只有一个抢到,不重复
                  │ 弹出到期任务
                  ▼
   检查 infra:delay:canceled (Set)  ──已取消──→ 跳过
                  │ 未取消
                  ▼
   执行任务 ──失败──→ 指数退避重试 2s→4s→8s (≤3次) ──耗尽──→ DLQ(medical.dlx.topic)
```

**改造前后对比**：
| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 存储 | JVM 堆 ConcurrentHashMap | Redis ZSET（持久化） |
| 重启恢复 | 重扫 DB，精度按天 | **毫秒级精确恢复** |
| 多实例 | 重复执行 | **Lua 原子 POP 不重复** |
| 失败重试 | 无，失败即丢 | 指数退避 ≤3 次 |
| 重试耗尽 | 静默丢弃 | **投递 DLQ 可追溯** |
| 可见性 | 无 | 监控 API + Actuator |

**任务类型**：服药提醒（前 5 分钟）、漏服检测（后 2 分钟）、邀请过期（48 小时）。

**配图建议**：中央 Redis ZSET 抢占流程图（如上），右侧改造前后对照表。这页展示"原理"，是技术深度亮点。

### P14 — U2/U3 服务治理【技术方案】

**核心句**：分布式锁防并发，限流降级保稳定

**U2 分布式锁（Redisson）**：
```
@DistributedLock(key="#taskId")  ← AOP 切面 + SpEL 解析键
  └→ Redisson RLock 加锁 → 执行临界区 → 释放
应用场景: 用药任务状态更新、家庭成员操作、AI 工具执行
```

|------|---------|
| /api/agent/chat/stream | 10 QPS |
| /api/ocr/* | 5 QPS |
| /api/agent/chat | 并发线程数 20 |

### P16 — 大模型/RAG 优化迭代历程【技术方案 · 重点 · 演变迭代】

**核心句**：问题驱动的 6 轮 AI 链路迭代优化

**迭代时间轴（6 节点，每点一句话 + 一个指标）**：
```
①可靠性    ②弹性保护      ③省Token     ④性能扩容        ⑤RAG治理          ⑥并发修复
三层LLM回退 Resilience4j   Chat缓存     aiExecutor       统一HttpClient     Flask async
+空响应重试  Retry/限流/熔断 MD5键TTL300s 8→20→50/200     +Redis缓存+bulkhead def→线程池
            ──────────────────────────────────────────────────────────→ 时间
                                                                        10并发吞吐
                                                                        0.2→1.06(5.3×)
```

**各轮要点**：
1. **三层 LLM 回退**：MedicalAgent → StreamingChatModel → 阻塞 ChatModel，逐级降级 + 空响应重试
2. **Resilience4j 弹性**：Retry 3 次 → RateLimiter 20/s → CircuitBreaker 50% 失败率熔断
3. **Chat 缓存**：MD5(userId+sessionId+message) 缓存键，短文本 TTL 300s
4. **线程池扩容**：aiExecutor 8→20→50/200，HTTP 状态码修复（429/504 不再伪装 200）
5. **RAG 治理**：统一 AiHttpClient 连接池、Redis 缓存（TTL 抖动+空值缓存+Redisson 锁防击穿）、bulkhead 限流
6. **并发修复（最新）**：Flask `async def`→`def` 走线程池，10 并发吞吐 0.2→1.06 req/s（**5.3×**）

**配图建议**：横向 6 节点时间轴（如上），右下角放并发修复前后柱状对比小图。
